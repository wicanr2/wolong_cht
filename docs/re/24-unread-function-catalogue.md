# 24 — 未讀函式目錄：252 支的證據與下手順序

**狀態：252 支未讀函式全部登記，附上由共用常式與 TALK 訊息取得的角色證據。
計數要排除本檔自己（§5），否則登記等於被算成讀懂。**

- 日期：2026-08-13
- 範圍：只驗松崗 DOS/V
- 原始 `KI.EXE` SHA-256：`fffeba985231cda4d636e93d10f598470b1f691d00275e4aa38e285893d43868`
- 原始 `KI.EXE.i64` SHA-256：`7b7c1aa67c47f99062cfdd4439b3423302808c874f929c3ea6f75ec564034c26`
- 工具：`tools/ida_call_trace.idc`、`tools/ida_hot_helpers.idc`、`tools/re_classify.py`
- 位址空間：IDA DOS/V linear address，segment base `0x10000`

## 1. 為什麼是目錄不是逐支解讀

[`21-function-census.md`](21-function-census.md) 量出 252 支函式沒被讀過。
逐支讀組語要很久，但**放著不動的代價是每一輪都不知道自己漏了什麼**——
「還沒解」與「我不記得解過」在動手那一刻長得一模一樣。

所以這一份先把每一支登記起來，附上能自動取得的證據，讓下一輪能挑著讀。
這份目錄回答的是「這支大概在做什麼、值不值得現在讀」，
**不回答「這支的規則是什麼」**——後者仍要逐支反組譯，寫進各自的 `docs/re/`。

數字要現況重跑，不要引用這裡的。**而且重跑時要排除目錄型文件**——
本檔逐支登記未讀函式，不排除的話它們會全部被算成「已寫進 `docs/re/`」（§5）。

## 2. 方法：讓遊戲自己說它在做什麼

這支程式的 UI 與流程函式幾乎都走同一個形式——**設常數，然後呼叫共用常式**：

```asm
mov cx, 16h / call sub_18853               ; 狀態列顯示訊息 #22
mov ax, 5 / mov cx, 4Dh / call sub_193E9   ; 5 項選單，選項文字在 #77
mov cx, 0Bh / call sub_18810               ; 顯示訊息 #11
```

**`sub_18810` 的索引在 `cx`，不是 `al`。** `al` 是變數值，跟訊息無關；
`cx` 原封傳給 `sub_1075B`，由它決定索引與 ×8 展開
（[`25`](25-message-variants-and-personnel.md) §1、§2）。

`TALK.DAT` 已全解（[`../formats/01-talk-dat.md`](../formats/01-talk-dat.md)），
所以把這些常數抽出來查表，就能用**遊戲自己的文字**判斷一支函式在做什麼。
這比從呼叫端的參數順序反推可靠得多——後者是間接證據，會推錯。

`tools/ida_call_trace.idc` 匯出全庫的「立即值 → 呼叫」軌跡，
`tools/re_classify.py` 把立即值配到後面最近的呼叫上再查 TALK 表。

> ⚠ **配對是啟發式的。** 16-bit 真實模式的慣例確實是「先設暫存器再 call」，
> 但同一個暫存器可能在中間被別的路徑覆寫，分支也可能跳過賦值。
> **表格裡的每一列都是「這支函式裡出現過這個組合」，不是「它一定這樣呼叫」。**
> 要當結論用就得回去讀那一段組語。

### 2.1 挑哪支共用常式來讀

挑選依據不是直覺，是「被未讀函式呼叫的次數」——認出一支共用常式，
所有呼叫它的函式就同時多一條證據。本輪最高的是 `sub_1895D`（20 支未讀函式呼叫它）。

**`sub_1895D`（`0001895D`，71 B，29 個呼叫點）— 繪矩形／視窗**

```asm
mov si, bx / mov di, dx / mov bp, cx    ; 幾何存進 si/di/bp
xor ah, ah / push ax
and al, al / jnz +2 / inc ah            ; al=0 時 ah=1
call sub_1D5D4
pop ax / add si, 2
and al, al / jz +9
  mov bx, si / mov dx, di / mov cx, bp
  call sub_10C14                        ; al≠0 才走這一支
mov bx, si / mov dx, di / mov cx, bp
shl bx, 1 / shl dx, 1 / shl cx, 1       ; 幾何 ×2
and al, al / jz +2 / mov ah, al
call sub_189DE                          ; 這一支會寫熱區圖
```

`al` 是樣式（呼叫端用過 `0x1E`、`0x1F`、`0x3D`、`0x51`、`0x93`），
`bx`／`dx`／`cx` 是幾何。**它尾端會呼叫 `sub_189DE`，而那一支寫熱區圖**
（[`22`](22-strategy-command-tree.md) §2）——所以「畫一個框」與
「把那個框登記成可點區域」是同一個動作。這解釋了為什麼原版可以任意重疊視窗
而不必重算命中判定。

推論等級：**強證據**。幾何與樣式的確切語意（`al` 各值對應什麼框）尚未逐一對過。

## 3. 目錄

每一列的「證據」欄是**觀察到的呼叫組合**，不是命名。空白代表這支沒有呼叫任何
已定案語意的共用常式——那不表示它不重要，只表示這個方法對它沒有輸出。

`B` 是函式大小（bytes），`呼叫者` 是直接呼叫它的位置數
（**不含間接分派**，見 [`21`](21-function-census.md) §7）。

## 4. 下手順序

不要從最大的開始讀。建議順序：

1. **有 TALK 訊息證據的**（表格裡帶「#N『…』」的那些）。訊息文字直接說明用途，
   讀起來最快，而且能立刻寫進 `docs/mechanics/`。
2. **被多支未讀函式呼叫的共用常式**。認出一支就替一片函式加上證據，
   槓桿最高。重算方式見 §2.1。
3. **呼叫者已被記錄的**（`21` §5 的表有這一欄）。上下文已知，不必先建立場景。
4. 其餘按模組整批讀——同一模組的函式共用資料結構，一起讀比跳著讀省。

**不要用「大小」當優先度。** `21` 已經量過：已解的偏向大函式，
剩下的缺口是大量中小型函式，單支看都不起眼，但它們構成了流程骨架。
[`22`](22-strategy-command-tree.md) 就是這樣挖出來的——
`sub_161CA` 只有 74 bytes，卻是整個戰略層的入口。

### ⚠ 目錄會把自己算進覆蓋率

這一份逐支登記了每個未讀函式，而覆蓋率是靠「符號有沒有出現在 `docs/`」算的。
**登記完的下一次重跑，這 252 支會全部從 T4 升級成 T1，缺口顯示成個位數。**
`re_classify.py` 因此預設排除本檔（`re_coverage.scan_mentions(exclude=…)`），
要看含目錄的原始數字才加 `--include-catalogue`。

**這是量測工具的通病**：把「已登記」當成「已完成」。
`21` 的覆蓋率表同樣要記得這一層——**數字降下來不一定是讀懂了，
也可能只是被寫進了某份清單。**
