# 23 — `*BGM.DAT` 音樂資源格式

**狀態：容器索引與曲塊的聲軌指標表 confirmed，兩版都逐 byte 對齊到檔尾且餘 0。
聲軌資料本身的事件編碼、`+0x02`／`+0x04` 兩張表的內容與音色語意仍未解。**

- 日期：2026-08-13
- 範圍：`BGM.DAT`、`OPENBGM.DAT`、`ENDBGM.DAT`、`OVERBGM.DAT`，`dosv` 與 `pc98` 兩版都驗
- `YNSOUND.COM`（dosv）SHA-256
  `e2c6a6a8576c4f2a96b7e3f156d7f48c9570ae03539fe9367adb78aebb364fa1`
- `BGM.DAT`（dosv 20,826 B）SHA-256
  `7a51c8b9a349b9e088f3796b70c268181c60bcebead70942f00e1621523dedc9`
- 工具：IDA Pro 9.4（`tools/ida.sh batch dosv YNSOUND.COM` ＋
  `tools/ida_ynsound_resource.idc`）；資料側以 `tools/py.sh` 驗證
- 位址空間：COM offset ＋ `0x10000` ＝ IDA linear

## 1. 來源：INT 61h 的 command `0x07`

[`17-dosv-audio-tsr.md`](17-dosv-audio-tsr.md) 已定案 `YNSOUND.COM` 的介面：
INT 61h handler 在 COM `0x0103`，以 `AH` 查 COM `0x0115` 的 word table。
該文件把 command `0x07`（COM `0x01F6`）標為「資源 layout parser，格式未知」。

IDA 沒有在這一區建立函式邊界（自動分析只認出 5 支函式），所以下面是從
資料庫讀出的原始 bytes 逐指令解出的。**位址與 bytes 可重查**，
`tools/ida_ynsound_resource.idc` 會把同一段 dump 出來：

```asm
000101F6  1E 50 53 51 56           push ds / ax / bx / cx / si
000101FB  E8 1A 01                 call  0x10318
000101FE  E8 3F 01                 call  0x10340
00010201  2E 8E 1E 92 09           mov   ds, cs:[0992h]      ; 資源段
00010206  2E 8B 1E 94 09           mov   bx, cs:[0994h]      ; 資源內起點
0001020B  BE 10 00                 mov   si, 10h
0001020E  8B 00                    mov   ax, [bx+si]         ; ← 六個聲軌指標
00010210  03 C3                    add   ax, bx              ;   相對 → 絕對
00010212  2E 89 84 E6 09           mov   cs:[si+09E6h], ax
00010217  46 46                    inc   si / inc si
00010219  83 FE 1C                 cmp   si, 1Ch
0001021C  72 F0                    jb    0001020E            ; si = 10h..1Ah，共 6 次
0001021E  BE 02 00                 mov   si, 2
00010221  8B 00 / 03 C3            mov ax,[bx+si] / add ax,bx
00010225  2E A3 9A 09              mov   cs:[099Ah], ax      ; ← +02 的表
00010229  46 46                    inc si / inc si           ; si = 4
0001022B  8B 00 / 03 C3            mov ax,[bx+si] / add ax,bx
0001022F  2E A3 9C 09              mov   cs:[099Ch], ax      ; ← +04 的表
00010233  B8 00 08 / 33 C0         mov ax,0800h / xor ax,ax
00010238  B9 06 00 / BB 02 0A      mov cx,6 / mov bx,0A02h
0001023E  2E 89 07 / 43 43 / E2 F9 mov cs:[bx],ax / bx+=2 / loop  ; 清六個聲軌狀態
00010245  2E C6 06 8C 09 3F        mov   byte cs:[098Ch], 3Fh
0001024B  2E 80 0E 9E 09 02        or    byte cs:[099Eh], 2
00010251  2E 80 26 9E 09 FE        and   byte cs:[099Eh], 0FEh
00010257  2E C6 06 68 0B 01        mov   byte cs:[0B68h], 1
0001025D  2E C6 06 69 0B 01        mov   byte cs:[0B69h], 1
00010263  5E 59 5B 58 1F C3        pop si/cx/bx/ax/ds / retn
```

三件事由這段程式直接定案：

1. **曲塊 `+0x10` 起是六個 16-bit 指標**（`si` 從 `0x10` 走到 `0x1A`），
   相對曲塊起點，載入時加上 `bx` 變絕對位址。
2. **`+0x02` 與 `+0x04` 各是一個 16-bit 指標**，同樣相對曲塊起點。
3. **另有六個聲軌狀態 word**（`cs:0A02h` 起）在解析時清零，與六個指標一一對應。

六這個數字對上 PC-98 的 OPN／YM2203：FM 3 聲 ＋ SSG 3 聲。
日文說明書第 3.5 節的「FM音源とSSG音源」已定案 PC-98 側是這顆
（[`../reference/01-jp-manual.md`](../reference/01-jp-manual.md)）。
**DOS/V 側的實際晶片仍未定案**，只知道聲軌數相同。

## 2. 容器：`BGM.DAT` 是 11 曲的索引檔

檔頭 `0x000`–`0x0FF` 是 **11 組 32-bit little-endian 的 (offset, length)**，
之後才是曲塊本體。

驗證方式是把索引整條走一遍：每一項的 `offset + length` 必須等於下一項的 `offset`，
最後一項的結尾必須等於檔案長度。**兩版都完全成立，餘 0 byte**：

| | 檔長 | 項數 | 首項 | 鏈接連續 | 末端 |
|---|---:|---:|---|---|---:|
| `dosv` | 20,826 | 11 | `0x0100` | ✅ | 20,826（差 0）|
| `pc98` | 20,790 | 11 | `0x0100` | ✅ | 20,790（差 0）|

`OPENBGM.DAT`、`ENDBGM.DAT`、`OVERBGM.DAT` **沒有這個索引**——
它們整個檔就是一個曲塊，`+0x10` 直接就是聲軌指標表。
所以判斷一個 `*BGM.DAT` 是不是容器，看 `+0x00` 是不是 `0x00000100` 即可。

`SOUND.DAT`（dosv 304 B／pc98 372 B）**不是這個格式**：既沒有索引，
`+0x10` 也不是合法指標。它走的是另一條路（`17` §5 的效果碼）。

## 3. 曲塊內部

相對曲塊起點：

| 位移 | 大小 | 內容 |
|---|---|---|
| `+0x00` | 2 B | 未解 |
| `+0x02` | 2 B | 指向靠近曲尾的一張表；載入時存進 `cs:099Ah`。**內容未解** |
| `+0x04` | 2 B | 指向另一張表；存進 `cs:099Ch`。它是曲塊的**最後一段**，長 `0x30` B。**內容未解** |
| `+0x06`–`+0x0F` | 10 B | 未解 |
| `+0x10`–`+0x1B` | 6 × 2 B | **六個聲軌的資料起點** |
| `+0x22` | — | 空聲軌共用的 stub。未使用的聲軌指標一律是 `34`（`0x22`）|
| `+0x30` | — | 第一段聲軌資料。`48`（`0x30`）是最常見的第一個聲軌起點 |

`34` ＝ 空聲軌是**強證據**而非 confirmed：它在所有未使用的槽位上一致出現
（11 曲 × 2 版 × 6 槽），但 stub 的 bytes 本身還沒讀。

兩點值得記著：

- **聲軌不必按檔內順序排**。dosv #5／#7 與 pc98 #5 的第 4 個指標才是 `48`。
  所以「第一個聲軌從 `0x30` 開始」是慣例不是規則，
  **要靠索引走，不能靠掃描找 `48`**。
- **pc98 從來沒用過第 6 軌**（11 曲的第 6 個槽全是 `34`），dosv 有五首用滿六軌。
  這是兩版音樂資料的實質差異，不是編碼差異。原因未解——
  可能是移植時重編曲，也可能是兩邊的第 6 軌本來就不同用途。
  **不要據此推論任何一版的硬體聲道數。**

兩版 36 B 的檔案大小差完全來自各曲長度不同，不是格式差異。

## 5. 未解

| 項目 | 現況 |

| 聲軌資料的事件編碼 | 完全未解。音高、長度、迴圈、包絡都還沒讀 |
| `+0x02`／`+0x04` 兩張表 | 機制已定案（parser 會存指標），內容未解。`+0x04` 那張固定 `0x30` B，是音色定義的候選但**沒有證據** |
| `+0x00`、`+0x06`–`+0x0F` | 12 B 未解 |
| DOS/V 的實際音源晶片 | `17` §4 有 register path，卡種仍未定案 |
| 曲號 ↔ 場景的對應 | `KI.EXE` 呼叫端傳哪個索引還沒對過 |

## 6. remake 邊界

本輪只解出結構，**沒有解出可聽的音樂**。remake 不得據此宣稱音色或時序 parity；
在事件編碼解出並能重播之前，任何聲音都要標成替代資產
（沿用 [`17`](17-dosv-audio-tsr.md) §6 的界線）。

結構已解的直接用途是：可以把 11 首曲子各自切出來當獨立單位處理，
以及在推廣片素材上明確指出「這一段來自 `BGM.DAT` 第 N 曲」。

## 7. 怎麼重跑

```sh
tools/ida.sh batch  dosv YNSOUND.COM                       # 建資料庫（雜湊見上）
tools/ida.sh script dosv tools/ida_ynsound_resource.idc YNSOUND.COM.i64
```

資料側的索引驗證是純 Python，不需要 IDA：走 `(offset, length)` 鏈，
檢查每項銜接與末端等於檔長。這條檢查對任何 `*BGM.DAT` 都適用，
**是這個格式最便宜的正確性判準**。
