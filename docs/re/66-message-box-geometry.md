## 1. 框：`sub_18810` 的兩個立即值

```asm
00018814  mov dx, 0Ah / mov bx, 8 / mov al, 1Eh / mov cx, 510h
0001881F  call sub_1895D              ; 畫框
00018827  mov dx, 0Ah / mov bx, 0Ah
0001882D  call sub_1075B              ; 畫肖像 ＋ 文字
00018839  … al = 0 … call sub_1895D   ; 用樣式 0 再畫一次 ＝ 擦掉
```

`sub_1895D` 的單位是 **16 px 粗格**，而且**內部把 Y 加 2 格**
（[`47`](47-main-screen-window-registry.md) §1）：

```
X ＝ dx × 16      ＝ 10 × 16 ＝ 160
Y ＝ (bx + 2) × 16 ＝ 10 × 16 ＝ 160
寬 ＝ cl × 16     ＝ 16 × 16 ＝ 256
高 ＝ ch × 16     ＝  5 × 16 ＝  80
```

⭐ **框 ＝ (160, 160, 256, 80)。**

### 1.1 兩個 `bx` 差 2 不是筆誤

畫框傳 `bx = 8`、畫字傳 `bx = 0Ah`，因為 `sub_1895D` 自己會加 2 格而
`sub_10BCD`（§2）不會。**兩條路算出來的 Y 都是 160 那一格**——
這是版面推導的一個免費交叉檢查。

## 1.5 `sub_1075B` 的兩個參數：`al` ＝ 肖像頁、`cx` ＝ TALK 索引

`sub_18810` 把呼叫端的 `al`／`cx` 原封不動傳下來。全量掃 `KI.EXE.asm` 的
**60 個 `call sub_18810`**：40 處傳固定的 `93h`（**通報者**那張臉，KAOGRF 第 147 頁），
20 處傳武將記錄 `+0x01`（**說話者**，幾乎都是 ≥`0x196` 的變體組，例外是 #58）。
`cx` 在 `0001075B` 開頭就做 ≥`0x196` 的 ×8 變體展開（`ah` 選組內第幾個）。
細節與 remake 的實作見 [`../spec/106`](../spec/106-message-box-reporter-portrait.md)。

## 2. 內容區：`sub_1075B` → `sub_10BCD`

`sub_1075B` 一進去就寫死 `mov cx, 510h`，再呼叫 `sub_10BCD` 清出內容區：

```asm
00010BD6  dx <<= 4 / bx <<= 4          ; 粗格 → 像素
00010BE6  dx += 8  / bx += 8           ; ★ 四邊各內縮 8 px
00010BEC  si = dx + (cl << 4) − 11h    ; 右界
00010BFB  di = bx + (ch << 4) − 11h    ; 下界
00010C0A  call sub_1F1A3               ; 填這個矩形
```

`dx = 0Ah`／`bx = 0Ah` 代入：**(168, 168) 到 (407, 231)**，
也就是 **240 × 64 px**。

⭐ **內容區 240 × 64 ＝ 15 全形字 × 4 列。** 減 `0x11` 是「兩邊各內縮 8，
再減 1 換成含端點的座標」。

## 3. 肖像與文字的位置

`sub_1075B` 的後半段（`bx`／`dx` 都是呼叫端傳進來的粗格值）：

| 目的 | 算式 | `sub_18810` 代入 |
|---|---|---|
| 肖像 X | `dx × 16 + 72` | **232**（右緣；64 寬 ⇒ 起點 168）|
| 文字 X | `dx × 16 + 80` | **240** |
| 文字 Y | `bx × 16 + 16` | **176** |

肖像走 `sub_10AD9`，尺寸 64×64（[`33`](33-shared-draw-helpers.md) §1：
每張 2,048 B ＝ 64×64 的 4bpp）。文字走 `sub_106F9`，
一個全形字前進 16 px（[`47`](47-main-screen-window-registry.md) §1）。

**文字可用寬度 ＝ 框右內緣 − 文字起點 ＝ (160+256−8) − 240 ＝ 168 px**，
放得下 **10 個全形字（160 px）**，剩 8 px。§6 的原文統計正好卡在這個數。

## 4. ⭐ `al` 是肖像頁，`ah` 是變體索引

`sub_1075B` 開頭 `push ax`，中間 `mov ah, 0 / call sub_10AD9`（肖像），
結尾 `pop ax / mov al, ah / mov ah, 0FFh / call sub_106F9`（文字）。

| 暫存器 | 用途 | 誰這樣傳 |
|---|---|---|
| `al` | **`KAOGRF` 頁碼** | `sub_13C99` 的 `mov al, [si+1]` ＝ 武將記錄 `+0x01` 頭像編號；`sub_13CDC` 的 `mov al, [bx+4241h]` 是同一個欄位 |
| `ah` | 訊息 ≥ `0x196` 時的**八格變體索引**，並傳給文字常式（算式見 §4.1）| `sub_13C99` 從武將 `+0x1E` 取（`≥3` 先減 3）；`sub_14D63` 直接傳原始值 |

⭐ **一般通知也有肖像。** `sub_18810` 的呼叫端幾乎清一色 `mov al, 93h`——
`0x93` ＝ 147，就是 `KAOGRF` 第 147 張。把它渲染出來，
與 `workplace/parity/f008-640.ppm` 上那張戴頭巾的臉是同一張圖。

### 4.1 `0x196` 之後每則佔八格

```asm
00010763  cmp cx, 196h / jb →
00010769  sub cx, 196h
0001076D  shl cx, 1 / shl cx, 1 / shl cx, 1   ; ×8
00010773  add cl, ah / adc ch, 0
00010778  add cx, 196h
```

⭐ **`cx` 在這個範圍裡是「第幾組」不是「第幾則」**：

```
實際索引 ＝ 0x196 + (cx − 0x196) × 8 + ah
```

`sub_14D63` 傳 `cx = 0x1A6` 拿到的是 **534 + 變體**——
537「至今的投資全都白費了！！」那一組。
⚠ `0x1A6` 的十進位是 422，而 #422 剛好是「．．．．」，
**誤讀成索引在語意上也講得通**，所以只能靠算式分辨。
remake 的對應是 `cmd/wlgame/battletalk.go` 的 `resolveBattleTalkIndex`。

> ⚠ 這個 `0x93` 先前被 `re_classify.py` 當成訊息索引，
> 於是全庫每個 `mov al, 93h` 都被翻成同一則不相干的訊息
> （`CLAUDE.md` §7 第 33 條）。**它是肖像頁，不是索引；索引在 `cx`。**

### 5.1 事件場景的兩個講話框，也在影格上量過了

事件 2／3 的畫面（`IVENTGRF` 288×176 的插圖 ＋ 兩個講話框）出現在
原版實錄影片的 4 分 30 秒（`workplace/promo-live/original-video/original.mp4`，
影格 956×720，遊戲區 `y 56..660`、`x 0..955`）。

兩支常式傳給 `sub_1075B` 的參數換算之後：

| 常式 | 誰在說話 | 參數 | 內容區（算） | 內容區（量） |
|---|---|---|---|---|
| `sub_13C99` | **呼叫端指定的武將**（進言時是君主）| `dx=0, bx=5` | (8, 88, 240, 64) | **y 87–151、右緣 249** |
| `sub_13CDC` | **一定是軍師**（勢力 `+0x02` → 武將 `+0x01`），也就是玩家自己 | `dx=8, bx=12h` | (136, 296, 240, 64) | **y 295–358、右緣 378** |

⭐ **兩個都落在量測誤差內**（影格的縮放是 1.494×／1.513×，非整數）。
換成框（內容區四邊各外擴 8）就是 **(0, 80, 256, 80)** 與 **(128, 288, 256, 80)**。

三個框的寬高完全一樣，差別只有位置——`sub_1075B` 把 `cx = 0x510` 寫死，
**版面是同一套，位置由呼叫端決定**。

### 5.2 進言的畫面流程：上框 → 下框 → 上框

`sub_13830` 是玩家進言時整個畫面的順序，兩個框輪流講話：

```asm
sub_13D09(al=0)                    ; 貼 IVENTGRF 第 0 頁（事件插圖）
sub_10241(al=6)
cx = base        / sub_13C99       ; ① 上框：君主問
cx = base + 3    / sub_13CDC       ; ② 下框：軍師說（玩家挑的理由）
al = 結果碼 / cx = base + al×3 + 4
  al > 3  → cx = 53h（TALK #83）/ sub_13C99 / STC
  al == 3 或 al == 0 → 信賴度 −20（`sub_13DC9`，al=14h）/ sub_13C99 / STC
  al == 1 → sub_13C99 / 信賴度 +20（`sub_13D91`）/ CLC
  al == 2 → sub_13C99 / base += 10h / sub_13B5A（多理由的下一輪）
```

⭐ **③ 君主的回答又回到上框**，索引是 `base + 結果碼×3 + 4`。
原版實錄影格上的那一幕就是這三步：上框「軍師，是要我出陣嗎？」→
下框「若請主公出陣，將士的士氣也會提高吧。」→
上框「好，來人啊，牽馬過來！我來大顯神勇！！」。

信賴度的 `±20` 就是 `mov al, 14h`，與
[`../mechanics/70-ai.md`](../mechanics/70-ai.md) §1 記的一致。

remake 對應在 [`../spec/45`](../spec/45-advise-scene-layout.md)：
插圖、上下兩個框、五列理由選單都照這個順序畫。

## 6. 原文本身就折好了，遊戲不換行

`TALK.DAT` 的 1,022 則訊息裡，**825 行剛好 160 px（10 全形字）**——
一個硬到不可能是巧合的群聚。行數分布：0 行 78、1 行 124、2 行 673、
3 行 141、4 行 2、5 行 4。

**5 行的那四則全是五選一的選單**（[`../playtest/32`](../playtest/32-talk-layout-fit.md) §2），
由選單常式畫，不進這個框。所以 **4 列容得下所有真的會進框的訊息**，
與 §2 的 64 px 內容高相符。

超過 160 px 的少數行都含 `{N}` 變數標記，那是插入點不是實際字寬。
