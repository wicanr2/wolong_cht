## 1. 主流程

```asm
sub_13E11:
    call sub_131AE           ; ① 事件分派（每 10 次呼叫才真正處理一筆）
    mov  si, ds:0D1Ch        ; ② 這一小時輪到的勢力
    mov  ds, cs:word_10D52
    cmp  byte ptr [si], 80h / jb .skip
    and  byte ptr [si], 0BFh
    mov  al, [si+23h] / …×8 + 18h…     ; 據點數 × 8 + 24
    cmp  ax, [si+21h] / jl .skip       ; vs 資金 >> 8
    mov  byte ptr [si+19h], 0FFh       ; ★ 資金不足 → **取消侵攻**
    shr  ax, 1
    cmp  ax, [si+21h] / jl .skip
    or   byte ptr [si], 40h            ; 更不足 → 再設一個位元
.skip:
    call sub_13E65           ; ③ 預備兵維持費
    call sub_13E8E           ; ④ 外交官
    add  si, 40h / cmp si, 580h / jb .1 / xor si, si
.1: mov  word_10D1C, si      ; 下一小時換下一個勢力
```

**每小時只處理一個勢力**，22 個勢力輪一圈 ＝ 22 小時（不到一天）。
所以「每個勢力每天大約被處理一次」。

### ⭐ 勢力 `+0x19` ＝ 侵攻／敵對目標（`0xFF` ＝ 無）

不是「財政警戒旗標」——**它存的是勢力編號**。三處證據：

| 位置 | 程式 |
|---|---|
| `sub_12E33` | `cmp dh, 0FFh` **以及** `cmp dh, cs:byte_10CFF`（與**玩家勢力編號**比） |
| `sub_13526` | `mov [si+19h], dl`，`dl` 是另一個勢力的編號 |
| `sub_135AB` | `mov [bx+19h], ah`，`ah` 是 `si` 那個勢力的編號 |

所以 `sub_13E11` 那段的意思是：

```
每小時輪到某個勢力時：
  若 資金 >> 8  <  據點數 × 8 + 24   →  取消侵攻（+0x19 = 0xFF）
  若更低（門檻減半）                →  再設 +0x00 的 bit 6
```

**⭐ 財政撐不住就自動取消侵攻。**
門檻與**據點數**掛鉤：地盤越大，維持一場侵攻需要的最低資金越高。

這條規則是說明書那幾個說服理由的底層機制：
「敵が他国侵攻中」「我が国防戦中」查的就是各勢力的 `+0x19`，
而「敵が疲弊中」（資金 < 0）之所以是好時機，正是因為
**對方的資金一旦掉到門檻以下，侵攻會自己停下來**
（`docs/mechanics/70-ai.md` §1.3、`50-diplomacy.md` §8）。

| 偏移 | 內容 |
|---|---|
| `+0x19` | **侵攻／敵對目標勢力編號**，`0xFF` ＝ 無 |
| `+0x00` bit 6 | 資金低於門檻一半時設起（用途未解） |

## 2. `sub_13E65`：預備兵維持費

```asm
xor dl, dl
mov ax, [si+4] / add ax, [si+6] / adc dl, 0 / add ax, [si+8] / adc dl, 0
…右移 5 次（÷32）…
call sub_15673            ; 累加到勢力 +0x1A／+0x1C（本月累計支出）
```

```
每次處理：累計支出 += (騎馬 + 弓兵 + 步兵) ÷ 32
```

`sub_15673` 是 `sub_15609`（收入入帳）的雙胞胎——同樣鉗在 `+655,000`，
只是寫進 `+0x1A`（累計支出）而不是 `+0x20`（資金）。

**這解掉了 `docs/re/07` §17 的「支出是誰累加的」。**
預備兵越多，每天扣得越多——正是說明書 5.2 的
「予備兵にも月単位で経費がかかり、月末に支払われます」。

## 3. ⭐ `sub_13E8E`：外交官的實際效果

```asm
mov  bh, [si+2Ah]                 ; 派駐這個勢力的外交官（武將編號）
cmp  bh, 0FFh / jz ret
call sub_1ECE0 / cmp al, 20h / jnb ret     ; 32/256 ＝ 12.5% 才動作
xor  bl, bl / shr bx,1 ×3         ; bx = 武將記錄
cmp  byte ptr [bx+425Ah], 0 / jz ret       ; 武將 +0x1A（經費餘額）＝ 0 → 不做事
mov  al, [bx+4253h]               ; 武將 +0x13 ＝ 政治
mov  ah, 17h / sub ah, al         ; 23 − 政治
sub  [bx+425Ah], ah               ; ★ 經費 −= (23 − 政治)
jnb  .1 / mov byte ptr [bx+425Ah], 0
.1:
call sub_1ECE0 / and al, 0Fh      ; 0–15
cmp  al, [bx+4253h] / ja ret      ; 亂數 > 政治 → 這次沒成果
…取交友度欄位…
and  ax, 807Fh
cmp  al, 64h / jnb .2 / inc al    ; ★ 交友度 +1，上限 100
.2: or al, ah / mov [bx], al
```

| 規則 | 值 |
|---|---|
| 動作機率 | **12.5%**（每次輪到時） |
| 經費消耗 | **23 − 政治** |
| 成功條件 | **`rand(0..15) ≤ 政治`** |
| 成功效果 | 交友度 **+1**，上限 **100** |
| 經費歸零 | 完全停止工作（要再要錢） |

### 政治值同時影響兩件事

**消耗速度**與**成功率**都吃政治。政治 15 的外交官每次只花 8 點經費、
成功率 16/16；政治 1 的每次花 22 點、成功率只有 2/16。

**這正是說明書 5.3 那句的機制**：

> 数値の高い武将の方が**成功したときの要求金額を少なく押さえる**ことができます。

說明書只講了「錢」，機器碼顯示它**同時**決定效率。

### ⭐ 交友度的儲存格式

```asm
and ax, 807Fh
cmp al, 64h        ; 100
```

**交友度是一個 byte：低 7 位是 0–100 的值，最高位元是旗標。**
`sub_1578F`（外交官要錢）也用同一個拆法（`and al, 7Fh` / `cmp al, 80h`），
高位元設定時基準是 100，否則 125。

### ⚠ 那個位元是「和平」不是「交戰」

把矩陣從 `SINARIO.DAT` 讀出來，極性一看就定了：

> 四個劇本裡**每一格的最高位元都是 1**，
> 而且**沒有任何勢力的 `+0x19`（侵攻目標）不是 `0xFF`**。
> 若 1 代表交戰，開局就會是二十二個勢力互相宣戰。

所以 **1 ＝ 和平、0 ＝ 交戰中**，`sub_1578F` 的基準也跟著讀通了：
和平 100、**交戰 125 —— 打仗時外交官要更多錢**。

### ⭐ `sub_13119` 的位址算法（交友度表的位置）

```asm
mov bx, si / shr bx,1 / shr bx,1        ; 觀察者 idx × 16
mov ax, bx / shr bx, 1 / add bx, ax     ; ×8 ＋ ×16 ＝ idx × 24
mov ax, di / shl ax,1 / shl ax,1
mov al, ah / xor ah, ah                 ; 對象 jdx
add bx, ax / add bx, 600h
```

```
交友度[觀察者][對象] ＝ 段內 0x600 ＋ 觀察者 × 24 ＋ 對象
                     ＝ 劇本檔 0x680 起，22 列 × 24 B
```

用史實驗過：劉備↔公孫瓚 **100**（同門）、孫策→劉表 **20**（父仇），
而劉表→孫策 **55**——最後這組正好證明**它是有向的**。
對角線是 **127**。詳見 `docs/formats/08` §1.55。

## 4. ⭐ `sub_16F26`：軍團編成

```asm
mov  bx, si / sub bx, 2240h / shl bx,1 ×2
mov  [si+2], bh                   ; 軍團編號
shr  bx,1 ×3 / mov di, bx
mov  byte ptr [di+4257h], 1       ; 武將 +0x17 ＝ 1（出陣中）
mov  bh, [di+425Ch]               ; 武將 +0x1C ＝ 所屬勢力
mov  [si+1], bh                   ; 軍團 +1 ＝ 所屬勢力
xor  bl, bl / shr bx,1 / shr bx,1 ; bx = 勢力記錄
mov  ah, [bx+3] / mov [si+20h], ah  ; 首都據點編號
cmp  byte ptr [si], 80h / jnb .1
inc  byte ptr [bx+14h]            ; ★ 勢力 +0x14 ＝ 軍團數
.1:
mov  byte ptr [si], 0C0h          ; 存在旗標
mov  byte ptr [si+8], 4
…ax = 首都據點編號 × 32…
mov  di, ax / add di, 840h
call sub_16F86                    ; 設定位置
mov  al, [bx+1Dh] / mov [si+6], al  ; ★ 勢力 +0x1D → 軍團 +6
mov  byte ptr [si+23h], 1
```

### 軍團記錄（**64 B**，段內 `2240h`，127 筆）

> 記錄是 **64 B**，三條證據：
>
> 1. `sub_125A3` 的迴圈 `add si, 40h`（64）並在 `cmp si, 1FC0h`（8128）繞回
>    —— **8128 ＝ 127 × 64**。
> 2. 欄位用到 `+0x23`（35），32 byte 放不下。
> 3. `sub_16F26` 用 `(si − 2240h) × 4` 的高位元組當軍團編號 ——
>    只有 stride 64 時 `idx × 64 × 4 = idx × 256` 才會讓 `bh` 剛好是 idx。
>
> ⚠ 但 `sub_15456`（AI 募兵判斷）用的是 `add bx, 20h` ＋ 127 次，
> **只掃得到前半段而且偏移全錯**。那看起來是原版的 bug，
> 也可能是我對那一段的解讀有誤。→ 待查，先照 64 記。

| 偏移 | 內容 | 等級 |
|---|---|---|
| `+0x00` | 存在旗標，建立時寫 `0xC0` | confirmed |
| `+0x01` | **所屬勢力** | confirmed |
| `+0x02` | 軍團編號 | confirmed |
| `+0x04` | AI 的募兵判斷會累加它（`docs/re/07` §8） | 強證據：兵力 |
| `+0x06` | **士氣值**，建立時從勢力 `+0x1D` 複製 | confirmed |
| `+0x08` | 建立時寫 `4` | 未解 |
| `+0x0A` | **行進方向**（`4` 走一條連結，其餘走另一條） | confirmed |
| `+0x0B` | **移動計時器**，每 tick 減 1，歸零就走一步 | **confirmed**（`sub_125A3`） |
| `+0x0C` | 行軍中的暫存（`sub_12708` 寫） | 未解 |
| `+0x0E` | **目前所在據點編號 × 8** | confirmed |
| `+0x10` | **目前 X** | confirmed |
| `+0x12` | **目前 Y** | confirmed |
| `+0x14` | **目標據點編號 × 8** | confirmed |
| `+0x16` | **目標 X** | confirmed |
| `+0x18` | **目標 Y** | confirmed |
| `+0x1A` | 佔用圖的 X | confirmed |
| `+0x1C` | 佔用圖的段位址 | confirmed |
| `+0x1E` | **移動間隔**（計時器歸零時從這裡重載）→ **就是「速度」** | **confirmed**（`sub_125A3`） |
| `+0x20` | 建立時寫首都據點編號 | 強證據 |
| `+0x23` | 建立時寫 `1` | 未解 |

**現在位置與目標位置是兩組獨立的三元組**（據點編號 ＋ XY），
行軍就是把前者往後者推進。

### ⚠ 修正：勢力 `+0x1D` 不是信賴度

先前把勢力記錄 `+0x1D`（四個劇本全部是 200）標成「疑似信賴度」。
**編成時它被複製進軍團的士氣值欄位**，而日文說明書 5.5 的編成畫面
截圖上士氣值正好是 **200**。

→ `+0x1D` 是**士氣基準值**，不是信賴度。信賴度存在哪還沒解。

## 5. ⭐ `sub_16F86`：軍團的位置與佔用圖

```asm
mov  ax, [di+8]  / mov bx, [di+0Ah]     ; 據點的 X、Y
mov  cx, di / sub cx, 840h / shr cx,1 / shr cx,1   ; 據點編號 × 8
mov  [si+0Eh], cx / mov [si+14h], cx    ; 現在與目標都設成這裡
mov  [si+10h], ax / mov [si+16h], ax
mov  [si+12h], bx / mov [si+18h], bx
xor  bh, bh / shl bx,1 ×3
mov  cx, bx / shl bx,1 / add bx, cx     ; bx = Y × 24（段）
add  bx, cs:word_19872
mov  [si+1Ah], ax / mov [si+1Ch], bx
mov  ds, bx / mov bx, ax
inc  byte ptr [bx]                      ; ★ 佔用圖 +1
```

**`word_19872` 那塊 98,304 B 是單位佔用圖。**

```
Y × 24 段 ＝ Y × 384 byte；X 是段內位移
384 × 256 ＝ 98,304 ✅
```

`docs/re/04` §2 把它記成「渲染用的畫布，尺寸與展開後的地圖相同」——
**尺寸猜對了，用途猜錯了**。它是每格一個 byte 的單位計數圖，
軍團進入時 `inc`、離開時應該 `dec`。

這也解釋了為什麼開機要把它整塊清零（`sub_119CA` 的 `rep stosw`）。

## 6. ⭐ 行軍：`sub_12662` ＋ `sub_127A2`

### 主流程（`sub_12662`）

```asm
mov  bx, [si+0Eh] / cmp bx, [si+14h]   ; 現在節點 == 目標節點？
jnz  .move
.arrived:
  mov  byte ptr [si+8], 4
  call sub_128F4                        ; 到達處理
  call sub_14325
  retn
.move:
  cmp  bx, 800h / jnb .offroad          ; 節點索引 < 256？
  mov  al, [si+1] / cmp al, cs:byte_10CFF / jz .2   ; 是玩家的軍團嗎
  call sub_14300 / jb .arrived          ; 非玩家 → AI 的行軍判斷
  jmp  .2
.offroad:
  call sub_142AB
.2:
  mov  dx, ds / lds di, [si+1Ah]
  dec  byte ptr [di]                    ; ★ 佔用圖 −1（離開這一格）
  …
```

**`dec byte ptr [di]` 證實了佔用圖是「進入 `inc`、離開 `dec`」的計數圖**
（§5 的推測成立）。

### 節點分三類

`[si+0Eh]` 存的是**節點索引 × 8**，兩個邊界把它分成三段：

| 節點索引 | `[si+0Eh]` | 意思 |
|---|---|---|
| 0 – 191 | `< 0x600` | **據點**（與據點表一一對應） |
| 192 – 255 | `0x600`–`0x7FF` | 路上的中間節點 |
| ≥ 256 | `≥ 0x800` | **野外**（走 `sub_142AB` 那條路徑） |

`sub_127A2` 只在 `< 0x600` 時去據點表拿座標：

```asm
mov  bx, [si+0Eh]
cmp  byte ptr [si+0Ah], 4 / jnz .1
mov  bx, es:[bx+8]        ; 走這條連結
jmp  .2
.1:
mov  bx, es:[bx+6]        ; 走另一條連結
.2:
mov  [si+0Eh], bx         ; 前進到下一個節點
cmp  bx, 600h / jnb .end  ; 是據點才更新座標
shl  bx,1 / shl bx,1
mov  ax, [bx+848h] / mov bx, [bx+84Ah]   ; 新據點的 X、Y
mov  [si+10h], ax / mov [si+12h], bx
…更新佔用圖位址…
.end:
mov  ax, [si+0Eh] / cmp ax, [si+14h]      ; 到了嗎
```

**行軍是在一張圖上一個節點一個節點走**，不是在格子上自由移動。
`[si+0Ah]` 決定走哪一條連結（`4` 走 `+8`，其餘走 `+6`）——
那是**行進方向**。

### ⚠ 連結表的記錄大小還沒定案

`es:[bx+6]` 與 `es:[bx+8]` 的 `bx` 是節點索引 × 8，
所以看起來每個節點 8 byte；但 `+8` 已經落在下一筆。
**兩個可能**：記錄其實更大（索引只是 ×8 的縮放），
或 `+8` 是刻意讀下一筆的 `+0`。
`es` 由 `sub_12662` 的呼叫者設定，還沒追。→ 下一輪

這張表很可能就是 `docs/formats/05` §3 記成「道路自動連接」的那批 8-byte 記錄
（`sub_1E68C` 寫進地圖格的那些）。若成立，**那不是繪圖用的連接，
是行軍用的道路網路圖**——又一個「尺寸猜對、用途猜錯」的候選。

## 6.5 ⭐ 軍團的每 tick 更新：`sub_125A3`

```asm
mov ds, cs:word_10D52
mov es, cs:word_19874        ; ★ 連結表所在的段（4,000 B）
mov si, cs:word_10D18        ; 上次處理到哪
mov cx, 10h                  ; ★ 一次只處理 16 個軍團
loop:
  cmp byte ptr [si+2240h], 80h / jb .dead
  add si, 2240h
  dec byte ptr [si+0Bh]      ; ★ 移動計時器 −1
  jnz .1
    mov al, [si+1Eh]         ; ★ 移動間隔 → 重載計時器
    mov [si+0Bh], al
    and byte ptr [si], 0DFh
    call sub_12662           ; ★ 走一步
  .1:
  call sub_12600 / call sub_1264A
  sub si, 2240h
  jmp .next
.dead:
  test byte ptr [si+2240h], 8 / jz .next / call sub_12A7E
.next:
  add si, 40h / loop
cmp si, 1FC0h / jb .2 / xor si, si     ; 8128 = 127 × 64
.2: mov cs:word_10D18, si
```

| 事實 | 意義 |
|---|---|
| **每次只處理 16 個軍團**，用 `word_10D18` 記進度 | 127 個軍團要 8 次呼叫才輪完一圈 |
| `+0x0B` 計時器每 tick 減 1，歸零才走一步 | **移動速度 ＝ `+0x1E` 的倒數** |
| `+0x1E` 是每個軍團自己的間隔 | 說明書「騎馬隊のみの軍団は移動速度が速くなります」就是給它較小的值 |

### ⭐ 連結表 ＝ `word_19874` 那塊 4,000 B

`docs/re/04` §2 列出開機時算好的六個緩衝區，其中最後一個
（`ds:9874h`，**4,000 B**）當時標「未解」。
`sub_125A3` 把它設進 `es`，而 `sub_127A2` 就是用 `es:[bx+6]`／`es:[bx+8]`
取下一個節點——**那塊 4,000 B 是行軍的連結表**。

4,000 ÷ 8 ＝ 500 筆；行軍用到的節點索引上限是 256（`cmp bx, 800h`），
所以前 2,048 byte 是實際會走到的部分。

⚠ `es:[bx+8]` 仍然落在下一筆的 `+0`。這一點還沒解釋——
可能是刻意的（兩條連結分別放在相鄰兩筆），也可能是我讀錯。

| `sub_15456` 用 stride 32 掃軍團表 | 與 64 矛盾，疑似原版 bug |
| `sub_14300`（AI 行軍判斷）、`sub_142AB`（野外移動） | 直接讀 |
| 軍團 `+0x0A` ＝ 行進方向的值域 | 直接讀 |
| 軍團 `+0x08`／`+0x23` | 建立時寫 4 與 1 |
| 信賴度存在哪 | 勢力 `+0x1D` 已排除（士氣基準）、武將 `+0x1D` 也已排除（捕虜狀態，見 `docs/re/09` §6） |
| ~~`sub_1310A` 怎麼算交友度欄位的位址~~ | ✅ `sub_13119`：段內 `0x600 + 觀察者×24 + 對象`（見 §3） |

## 7.1 ⭐ 建表迴圈是 **192 次**，不是 4,096 次（2026-08-08）

上一版卡在「掃 4,096 筆 × 2 B ＝ 8,192 > 4,000」對不上，並把
「`byte_1E47E` 是誰設的」列為要先查的問題。查到了：

```asm
sub_1E48A:                       ; MMAP 載入器
    …
    mov cs:byte_1E47E, 0C0h      ; ★ 0xC0 = 192
    mov cs:byte_1E47F, 0

sub_1E717:                       ; 建表迴圈
loc_1E76B:
    inc si / inc si              ; 輸出索引 +2（word）
    add bx, 8                    ; 下一筆 8-byte 記錄
    inc cs:byte_1E47F            ; 0 往上數
    dec cs:byte_1E47E            ; 192 往下數
    jnz loc_1E734

sub_1E567:                       ; 填一筆
    mov [si], di / mov [si+2], bp / mov [si+4], cx
    mov [si+6], ah / mov [si+7], al
    mov es, dx
    mov al, cs:byte_1E47E
    mov es:[di], al              ; ★ 把計數器**蓋進地圖格**
```

**192 正是據點數。** 所以：

| 舊的推算 | 實際 |
|---|---|
| 掃 4,096 筆 → 8,192 B | **192 圈 × 8 B ＝ 1,536 B** |
| 與 4,000 B 對不上 | 落在 4,000 B 之內 ✅ |

而且與 §6 已知的節點分類完全自洽：**節點 0–191 是據點**、192–255 是路上、
≥256 是野外，而行軍的上限判定是 `cmp bx, 800h`（0x800 ＝ 256 × 8）。
**這個迴圈填的就是「據點」那一段**。

> ⚠ 教訓：那個「8,192 > 4,000」的矛盾不是資料有問題，
> **是我拿了一個沒查證的迴圈次數去推算容量**。
> 算出矛盾時第一個該懷疑的是輸入的假設，不是結論。

`sub_1E567` 還會把計數器寫回地圖格（`mov es:[di], al`）——
所以地圖格上帶著節點編號，這與 `docs/formats/05` §3 記的
「把道路格蓋成節點流水號」是同一件事。**兩份文件講的是同一個機制。**

### ⭐ 迴圈體是手動展開 ×4 —— 一圈處理**四個方向**

`sub_1E717` 的迴圈體把同一段程式碼**抄了四次**：

```asm
loc_1E734:
    cmp byte ptr es:[bx+7], 80h / jb .1 / call sub_1E77D   ; 方向 1
.1: inc si / inc si / add bx, 8
    cmp byte ptr es:[bx+7], 80h / jb .2 / call sub_1E77D   ; 方向 2
.2: inc si / inc si / add bx, 8
    cmp byte ptr es:[bx+7], 80h / jb .3 / call sub_1E77D   ; 方向 3
.3: inc si / inc si / add bx, 8
    cmp byte ptr es:[bx+7], 80h / jb .4 / call sub_1E77D   ; 方向 4
.4: inc si / inc si / add bx, 8
    inc cs:byte_1E47F / dec cs:byte_1E47E / jnz loc_1E734
```

所以**一圈 ＝ 一個據點 ＝ 四筆記錄**：

```
192 圈 × 4 筆 × 8 B = 6,144 B   ← 來源表（es 段）
192 圈 × 4 筆 × 2 B = 1,536 B   ← 輸出的連結表（落在 4,000 B 之內 ✅）
```

**768 筆正是 `docs/formats/05` §3 記的那個數字**（「掃四個方向建 768 筆
8-byte 記錄」）。兩份文件講的是同一張表的兩端：`docs/formats/05` 講的是
**怎麼建來源表**，這裡講的是**怎麼把它壓成行軍用的連結表**。

| 欄位 | 內容 |
|---|---|
| 來源 `es:[bx+7]` | 旗標，`≥ 0x80` 才有連結（`jb` 就跳過，那個方向沒有路） |
| 來源 一筆 8 B | 四筆一組，對應**四個方向** |
| 輸出 `ds:[si]` | 一個方向一個 word |

### ⭐⭐ 訂正：連結表的一筆是 **16 byte**，不是 8

`sub_1E77D`（填表）的最後一行是 **`add di, 10h`**——輸出游標一次前進
**16 byte**，而且從 `di = 800h` 開始。

**這推翻了「`es:[bx+8]` 落在下一筆的 `+0`」那個疑問**：
一筆是 16 byte 的話，`+8` 本來就在**同一筆之內**。
先前把它當成「讀到下一筆、可能是我讀錯」，是因為假設了一筆 8 byte。

> ⚠ 這個假設從哪裡來的：**來源表**確實是 8 byte 一筆（`add bx, 8`），
> 而我把來源的筆寬套到了輸出上。
> **同一條管線的兩端不必同寬**——這是很容易滑過去的一步。

`di = 800h` 這個起點也自洽：`0x800 = 2,048 = 256 × 8`，正是
§6 那個 `cmp bx, 800h` 的邊界。所以 4,000 B 那塊的佈局是

```
0x000–0x7FF   每個節點一筆 8 B 的索引（256 個節點）
0x800 起      16 B 一筆的連結記錄
```

### 已定案的三件事

| 事實 | 依據 |
|---|---|
| **一條路只會被建一次** | 填完之後回頭找反向的那一筆（比對 `cx`／`dx`）並把它的 `+7` 旗標清成 0 —— 從另一端掃到時就會被 `jb` 跳過 |
| 索引裡存的是**帶標記的指標** | `[si] = di \| 0x4000`、`[bx+si] = di \| 0x8000`。兩個高位元區分「指向哪一張表」 |
| `[di+6]` 是**回指來源** | `mov ax, si / and al, 0F8h` —— 對齊到 8 的倍數，也就是回指**那個據點的四方向那一組** |

### ⭐ 16 byte 的欄位全解：`sub_1E81C` 是「沿著路走一遍」

`sub_1E81C` 拿著座標沿道路推進，方向由 `dh & 0x0F` 決定：

| `dh & 0F` | 動作 | 意思 |
|---|---|---|
| 0 | `dec cx` / `dec si` | X − 1（西） |
| 1 | `inc cx` / `inc si` | X + 1（東） |
| 2 | `dec dl` / `sub si, 180h` | Y − 1（北） |
| 其餘 | `inc dl` / `add si, 180h` | Y + 1（南） |

**`0x180 = 384 = 地圖寬**——`si` 是 `y × 384 + x` 的線性索引，
與 `docs/formats/05` §2 的地圖尺寸完全對上。

走的過程中它同時做兩件事：

1. 每一步把 `(cx, dl, 旗標)` 寫成一筆 **4 byte 的路徑點**，
   寫進 `word_1E480` 指的緩衝區（從 `0x2000` 起跳、每筆 `add bx, 4`）。
2. 維護四個全域的 **min/max**（結尾那幾組 `cmp` ／ `mov`）：
   `word_1E484`／`word_1E486` 是 X 的最小／最大，
   `byte_1E488`／`byte_1E489` 是 Y 的最小／最大。

`sub_1E77D` 把這四個抄進記錄——**所以 `+0Ah`–`+0Fh` 是這條路的外接矩形。**

### 連結記錄（16 byte）

| 偏移 | 型別 | 內容 | 等級 |
|---|---|---|---|
| `+0x00` | word | 路徑點緩衝區的**起點** | 強證據 |
| `+0x02` | word | 路徑點緩衝區的**終點**（`bx − 4` ＝ 最後一筆） | 強證據 |
| `+0x04` | byte | `sub_1E81C` 的回傳 `ah` | 未解 |
| `+0x06` | word | **回指來源**那個據點的四方向組（`and al, 0F8h`） | 強證據 |
| `+0x08` | word | 另一張表的索引（`bx << 3`） | 未解 |
| `+0x0A` | word | 這條路的 **min X** | 強證據 |
| `+0x0C` | word | **max X** | 強證據 |
| `+0x0E` | byte | **min Y** | 強證據 |
| `+0x0F` | byte | **max Y** | 強證據 |

外接矩形這一組是有用途的線索：**「軍團現在在不在這條路上」用矩形先篩
比逐點比對便宜得多**，而行軍正需要這種查詢。（用途未驗，先標假說。）

### ⚠ `cmp al, 0D4h` 比的**不是圖塊值**

`0xD4` ＝ 212，很接近戰場編號的值域 `0xCF`–`0xD5`（`0xCE` ＋ 地形類型 1–7，
`docs/re/05` §3）。**那是巧合，不要接上去。**

`sub_1E81C` 讀的 `es:[si]` 與 `sub_1E567` 寫的 `es:[di]` 是**同一塊緩衝區**，
而 `sub_1E567` 往那裡寫的是 `byte_1E47E` ——**節點編號**（192 往下數），
不是圖塊值。所以這個門檻比的是節點編號的分段。

與 §6 已知的節點分類擺在一起看：

```
0–191    據點     （0x00–0xBF）
192–255  路上     （0xC0–0xFF）  ← 0xD4 落在這一段裡面
≥256     野外
```

**`0xD4` 是「路上」那一段內部的一個分界**，不是據點與路的分界。
它切開的是什麼還沒解——但至少可以排除「圖塊值」與「戰場編號」兩條線。

> 這一則記下來是因為**數值的巧合是最貴的誤導**：212 同時落在
> 「戰場編號 0xCF–0xD5」與「路上節點 0xC0–0xFF」兩個區間裡，
> 而只有後者與這段程式碼共用同一塊記憶體。
> **判斷一個常數屬於哪個值域，看它跟誰共用緩衝區，不要看它落在誰的區間。**

⚠ 仍未解：`+0x04`、`+0x08` 兩格，以及 `0xD4` 切開的是什麼。

## 7.2 ⭐ `+6` 與 `+8` 是同一個節點的**兩個方向**（2026-08-08）

用「誰讀它」定語意，不是「誰寫它」。讀的是 `sub_127A2`：

```asm
mov bx, [si+0Eh]                 ; 軍團的現在節點（已經是 ×8 的偏移）
cmp byte ptr [si+0Ah], 4         ; ★ 軍團 +0x0A ＝ 沿路徑表前進的步進量
jnz .else
    mov bx, es:[bx+8]            ;   ＝ 4 → 取 +8
    jmp .store
.else:
    mov bx, es:[bx+6]            ;   否則 → 取 +6
.store:
mov [si+0Eh], bx                 ; 更新現在節點
cmp bx, 600h / jnb .skip         ; ★ 0x600 ＝ 1,536 ＝ 192 × 8 → 是**據點**
    shl bx,1 / shl bx,1          ;   ×4 → 據點編號 × 32
    mov ax, [bx+848h]            ;   據點記錄 +8  ＝ X
    mov bx, [bx+84Ah]            ;   據點記錄 +10 ＝ Y
    mov [si+10h], ax / mov [si+12h], bx    ; 寫進軍團的現在座標
.skip:
mov ax, [si+0Eh] / cmp ax, [si+14h]        ; 到達目標節點了嗎
jnz ret
mov byte ptr [si+8], 4                     ; 軍團 +0x08 朝向 → **4 ＝ 靜止**
```

### 三件定案

| 事實 | 依據 |
|---|---|
| **`+6`／`+8` 是兩個方向的下一個節點**，軍團 `+0x0A` 選哪一個 | `cmp [si+0Ah], 4` 的兩支各取一個 |
| `cmp bx, 600h` 的 `0x600` ＝ **192 × 8** | 與「節點 0–191 是據點」完全一致；只有據點節點才有座標可取 |
| 據點記錄 `+8` ＝ X、`+10` ＝ Y | `[bx+848h]`／`[bx+84Ah]` ＝ 據點表基址 `0x840` ＋ 8／＋10。**與 `docs/formats/08` §1.6 獨立互證** |

### ⚠ 這順帶解釋了「`+8` 落在下一筆」那個疑問的**另一半**

`docs/re/08` §6 原本記的 `es:[bx+8]` 是**這張每節點 8 byte 的索引表**，
不是 §7.1 那個 16 byte 的連結記錄——**兩個 `+8` 是不同的東西**。

- 索引表（`0x000`–`0x7FF`，每節點 8 B）：`+6`／`+8` ＝ 兩個方向。
  `+8` 確實落在下一筆的 `+0`，**而那是刻意的**——
  一筆 8 byte 只放得下 `+0`…`+6`，第二個方向借用下一筆的頭。
- 連結記錄（`0x800` 起，每筆 16 B）：`+8` 在同一筆之內（§7.1）。

> 先前把兩者混為一談，是因為兩張表在同一塊 4,000 B 裡，
> 而 `+8` 這個偏移在兩邊都出現。**同一個偏移在不同表裡不是同一件事。**

**`+0x04`、`+0x08` 已補齊，見 §7.3。**

## 7.3 ⭐ 連結記錄補齊：`+04` 是路徑點數、`+08` 是終點節點

### `+0x08` ＝ 終點節點 × 8

`sub_1E77D` 的尾段：

```asm
mov bl, es:[si]        ; 從地圖緩衝區取**對面那一格的節點編號**
xor bh, bh
shl bx,1 / shl bx,1 / shl bx,1     ; × 8
mov [di+8], bx                     ; ★ +08 = 終點節點 × 8
mov ax, di / or ah, 80h
mov [bx+si], ax                    ; 順手把**反向**的索引也填好
```

配上開頭的 `mov ax, si / and al, 0F8h / mov [di+6], ax`
（`si` ＝ 據點 × 8 ＋ 方向 × 2，遮掉低 3 位就是**起點節點 × 8**），
這兩格是對稱的：

```
+06  起點節點 × 8
+08  終點節點 × 8
```

**一筆連結記錄就是一條路的兩端。** 而 `[bx+si] = di | 0x8000` 是
把反向那一格的索引也一併填好——所以一條路只走一次就把雙向都建起來了
（配合 §7.1 那個「填完清掉反向旗標」的動作，完全自洽）。

### `+0x04` ＝ 這條路有幾個路徑點

`sub_1E81C` 的迴圈尾段：

```asm
mov [bx], cx / mov [bx+2], dl / mov [bx+3], al   ; 寫一筆 4 B 的路徑點
…更新四個 min/max…
add bx, 4                                        ; 下一個路徑點槽
inc ah                                           ; ★ 步數計數
and al, 7 / cmp al, 1 / ja 繼續走
```

**`ah` 從 0 開始，每走一格 `inc` 一次**，回來之後被 `sub_1E77D` 存進 `[di+4]`。
所以 `+04` 是這條路的路徑點數——與 `+00`／`+02`（起訖）冗餘，
但省掉了「終點減起點再除以 4」那一步。

### `cmp al, 0D4h` 與迴圈的終止條件

走的終止條件是 **`(al & 7) ≤ 1`**（`and al, 7 / cmp al, 1 / ja`），
`al` 是地圖緩衝區那一格的值。而進入時的 `cmp al, 0D4h / jb` 決定
要不要**先把 `al` 強制成 4** 再開始走——`4 & 7 = 4 > 1`，所以強制成 4
等於「無條件先走一步」。

換句話說：`0xD4` 不是節點分類的界線，而是**「這一格要不要當成起步格」**
的判定。真正決定路走到哪裡結束的是低 3 位。

> ⚠ 上一輪把它記成「路上節點內部的一個分界」。方向對了（確實是節點值不是圖塊值），
> 但**用途猜錯**：它管的是起步，不是分類。
> 又一次「值域猜對、用途猜錯」——這個專案的常見形狀。

## 7.4 據點記錄裡的鄰接不是道路網

拿 `+0x00` 的低 4 位配 `+0x1C`–`+0x1F` 把 192 個據點的鄰接關係展開：

| 量到的 | 值 |
|---|---|
| 有向邊 | 170 |
| **雙向都記著的** | **170 / 170（全部）** |
| 無向邊 | 85 |
| 有鄰接資料的據點 | 115 / 192 |
| **連通分量** | **108 個**，最大的一個只有 17 個據點 |

```
樂陵 臨淄 挺 北海 東莞 東武 瑯邪
漆 臨晉 槐里 長安 潼關 安陽 新城
合肥 牛渚 舒縣 濡須口 皖城 廬江 潯陽江
```

**這張圖不能拿來找路**——從長安走不到洛陽。

那四格存的是「直接相鄰、中間沒有路節點」的那些。完整的道路網是
`sub_1E717` 在載入 `MMAP` 時**現建**的（§7.1），節點包含
據點（0–191）、路上（192–255）與野外（≥256），
把兩個據點連起來的往往是中間那些路上節點。

## 7.5 地圖格的語意

| 圖塊值 | 全圖格數 | 是什麼 | 走訪 |
|---|---:|---|---|
| `0xB8`–`0xB9` | 159 | 道路 | 繼續 |
| `0xBA`–`0xCA` | 4,859 | 道路 | 繼續 |
| `0xCB`–`0xD3` | **192** | **據點的節點格**（＝ 據點數）| 停 |
| `0xD4`–`0xDD` | **508** | **城門格** | 停 |
| `0xCE`–`0xFF` 之中的其餘值 | — | **城池與地形圖形** | 不可走 |

判定式是 `(類別 & 7) ≤ 1` 才繼續（`sub_1E961`，分類見 §7.7）。

**`0xFE`／`0xFF` 是城池圖形。** 全圖 84 格 `0xFF`，
成 2×2 貼著 `0xFE` 圍在節點格外面：

```
y= 8   E6 FF FE FF F6
y= 9   DD FE CD FE F6      ← CD 是節點格，DD 是西邊的城門格
y=10   E6 FF FE FF F6
```

### 節點格的位置

據點記錄的 `(X, Y)` 是**城圖左緣**，節點格在 `(X + 4, Y)`
（191/192 個是 `+4`，剩下一個是 `−4`）。

### 道路是 8-連通的

只用四方向的話 192 個據點散成 **233 群**，八方向收到 **29 群**。
道路在畫面上是階梯狀的，轉折處靠對角相接。
`sub_1E81C` 找下一格時依序試西／東／北／南／西北／東北／西南／東南。

> 道路本身**不必彼此連通**——它們在城門格終止，
> 城門格屬於哪個據點是另外查的。連通性是圖層的事，不是格子層的事。

## 7.6 路徑點層級的三個坑

實作見 §7.7。這三件事與用哪個演算法無關，都要處理。

### 兩端要補一小段

節點格在 `(X+4, Y)`，而軍團的位置用的是據點記錄的 `(X, Y)`。
少了這一段，軍團出城與進城時會**跳好幾格**。

### 反向序列不是「直接反轉」

`A→B` 的序列約定是「不含 A、含 B」。直接反轉會得到「含 B、不含 A」——
**方向對了，但頭尾各錯一格**。正確做法是反轉之後去掉原本的 B、
再把 A 的格子接到尾巴（`reversePath`）。

這種 off-by-one 不會讓任何東西看起來壞掉：軍團照樣會抵達，
只是每經過一個中繼據點就偏一格。

### ⭐ 四條測試的共通點：都不看「有沒有抵達」

| 測試 | 抓什麼 |
|---|---|
| `TestRoadPathStaysOnRoad` | 逐格檢查圖塊值——路徑不能穿過山河 |
| `TestRoadPathIsContiguous` | 相鄰兩格必須 8-連通，且終點等於目的地座標 |
| `TestReversePathEndsAtOrigin` | 反向序列的 off-by-one |
| `TestMarchFollowsRoads` | 逐格連續 ＋ 走的格數不能少於路線段數 |

這一段所有的錯法（瞬移、抄近路、穿過河、偏一格）**軍團最後都會抵達
目的地**——用終點當斷言等於什麼都沒驗。

## 7.7 ⭐⭐⭐ 忠實呈現：把原版的走法整條移植過來（2026-08-08）

`internal/assets/world/roads.go` 是 `sub_1E4CE`／`sub_1E57F`／
`sub_1E81C`／`sub_1E961` 的直接移植。下面先說明為什麼不能用最短路代替。

### 逐條比對的結果

| 項目 | 值 |
|---|---|
| 邊的集合 | **完全相同**（253 條，兩邊各自沒有獨有的） |
| 路徑長度差 > 2 格的邊 | **109 / 253 ＝ 43%** |
| 全部路徑總長 | 原版 5,474 格 ／ BFS 4,777 格 |

原版**一律比較長**，因為它照著畫出來的路走；BFS 會抄近路。
最誇張的幾條：

```
漢夏 – 且蘭   原版 66 格 vs BFS 45 格
晉陽 – 平陽   原版 44 格 vs BFS 29 格
南昌 – 盧陵   原版 53 格 vs BFS 39 格
```

⭐ **「拓樸一樣」不等於「路一樣」。** 邊的集合完全相同，
所以所有的圖層檢查（85/85、連通性、分支度 ≤ 4）BFS 都通得過——
**那三條檢查對這個差異完全無感**。要看見它只能逐條比路徑本身。

### `sub_1E961`：圖塊分成四類

```asm
cmp si, di   / jz .拒絕        ; ★ 不能走回上一格
al = es:[si]
cmp al, 0B8h / jb .拒絕
cmp al, 0DDh / ja .拒絕
dl = 1 ; cmp al, 0BAh / jb .回傳   ; 類 1  0xB8–0xB9
dl = 0 ; cmp al, 0CBh / jb .回傳   ; 類 0  0xBA–0xCA
dl = 3 ; cmp al, 0D4h / jb .回傳   ; 類 3  0xCB–0xD3
dl = 4                             ; 類 4  0xD4–0xDD
.回傳: cmp al, 0CAh / jnz / or dl, 80h
```

走訪繼續的條件是 `(類別 & 7) ≤ 1` → **類 0／1 繼續，類 3／4 停**。

| 類 | 值域 | 全圖格數 | 是什麼 |
|---|---|---:|---|
| 1 | `0xB8`–`0xB9` | 159 | 道路 |
| 0 | `0xBA`–`0xCA` | 4,859 | 道路 |
| 3 | `0xCB`–`0xD3` | **192** | **據點的節點格** |
| 4 | `0xD4`–`0xDD` | **508** | **城門格** |

### 城門格：508 這個數字自己對上了

`sub_1E57F` 對節點格的四個方向各找一格路口，**先試 1 格再試 2 格**
（城門不一定緊貼節點格）。照這個規則數出來的城門格是 **508 個**，
與類 4 的圖塊數**一格不差**。

⭐ 兩邊算法完全無關：一邊是「從 192 個節點往四個方向找」，
另一邊是「掃全圖數某個值域」。數字對上代表
**「類 4 ＝ 城門格」這個讀法是對的，而且沒有漏找任何一個**。

### 走法的兩條規則都是行為的一部分

1. **不能走回上一格**（`cmp si, di / jz`）。`di` 是靠
   `push si` … `pop di` 每一步更新的。少了它會原地來回。
2. **八個方向有固定優先序**：西 → 東 → 北 → 南 → 西北 → 東北 → 西南 → 東南。
   分岔時走**第一個能走的**，不是走最近的。
   **換個順序會得到一條不同的路，而長度看起來還是差不多**——
   這種差異不會讓任何測試變紅。

### 移植後的數字

`internal/assets/world/roads.go` 現在是這四支常式的直接移植。

```
253 條邊，路徑總長 7,822 格（含頭尾城內那一小段），最長一條 94 格
最長路線（據點 0 → 143）：631 格、26 個據點
越界 0 格、不連續 0 處、終點座標吻合
```

> ⚠ 移植時踩到一個平面陣列特有的坑：`si ± 1` 在**列邊界會繞到
> 下一列的另一端**。原版的地圖定址是分段的（一列一段），天然二維，
> 不會有這個問題。實測有一條路因此從 `(383,190)` 跳到 `(0,192)`，
> 而且**憑空多出一條邊**（會稽–章安）——Python 原型當時報「原版 254 條、
> BFS 253 條」，那第 254 條就是這個 bug 生出來的。
> 加上 x 位移限制之後兩邊都是 253 條。
> **「多找到一條」比「少找到一條」更容易被當成好消息。**

### 這一項到此結束

軍團走的是原版地圖上、用原版演算法找出來的**那一條**路。
剩下的差別只有「玩家可以直接點遠處的據點」（原版只能點相鄰的），
那是操作方式，已經記在 `internal/rules/march` 的 package 註解裡。
