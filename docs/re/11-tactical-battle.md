# 11 — 戰術戰鬥：模組結構與戰場資料模型

**狀態：模組骨架與戰場資料模型已解。戰鬥規則本身還沒解。**

- 日期：2026-08-08
- 輸入：`workplace/ida/dosv/KI.EXE.i64`、`BATTLE.MAP`、`BATTLE.MDL`
- 前置：`docs/re/09`（戰略層的戰鬥）、`docs/formats/07`（`BATTLE.*` 分段）

戰術層是本作最大的一塊未解區域，約 15 KB 的程式碼、上百個函式，
而且用了自我修改碼。這一份不假裝解完了——它做兩件事：
**把模組的骨架畫出來**，讓下一趟不必再從入口摸起；
**把戰場的資料模型解到可以驗證的程度**，那是戰術層一切規則的地基。

## 1. 入口與主迴圈

```asm
sub_11B5A:                    ; 戰略層呼叫這裡（docs/re/09 §10）
  call sub_12078
  mov ax,2 / call sub_20000   ; 滑鼠：隱藏游標
  call sub_10A1C
  call sub_19946              ; ★ 戰場初始化
  call sub_19FA0              ; ★ 主迴圈，回傳 al ＝ 勝方

sub_19FA0:
  mov word_1D340, sp          ; 存 sp —— 結束時用它跳出來，不是正常回返
  mov ax,1 / call sub_20000   ; 滑鼠：顯示游標
  call sub_1A1C5
.loop:
  call sub_1A156              ; 讀滑鼠 → bx ＝ 按鍵
  test bx, 3 / jz .tick
    call sub_1E453
    cmp bx, 1 / jnz .right
    call sub_1BFF2            ; 左鍵
    jmp .tick
  .right: call sub_1C01D      ; 右鍵
.tick:
  call sub_1A426              ; ★ 執行一個腳本指令
  call loc_1A065              ; ★ 每幀更新 ＋ 繪製
  jmp .loop
```

**主迴圈沒有出口。** 結束是把 `word_1D340` 寫回 `sp`——
所以戰鬥的任何一層都能直接跳出來，不必逐層回返。
找「戰鬥怎麼結束」要找 `mov sp, cs:word_1D340`，不是找 `retn`。

### ⚠ `loc_1A065` 有自我修改碼

```asm
loc_1A065:
  cmp byte ptr ds:0D348h, 0
byte_1A06A db 74h              ; ← sub_19A33 執行期寫進來的 `jz`
```

`sub_19A33` 裡有 `mov byte_1A06A, 74h`——它在**執行期**把一個位元組
寫成 `jz` 的機器碼。IDA 靜態看到的是資料，後面幾行整段反編錯。
讀這一段要手動解位元組，**不要相信反編結果**。

## 3. 每幀執行一個指令：`sub_1A426`

```asm
cmp cs:word_1D313, 0 / jz .run
dec cs:word_1D313 / retn       ; ★ 等待中：這一幀什麼都不做
.run:
mov ds, cs:word_1D30C          ; 指令佇列的段
mov si, cs:word_1D311          ; 讀取位置
mov ax, [si]                   ; 一個 word 就是一個指令
mov bl, al / and bl, 1Fh       ; 低 5 位 ＝ 指令碼（0–31）
shl bx, 1
and al, 0E0h / rol al,1 ×3     ; 高 3 位 ＝ 參數（0–7）
inc si / inc si
call cs:funcs_1A457[bx]        ; 19 個指令
mov cs:word_1D311, si
```

指令佇列只有 **256 byte**（128 個 word），戰鬥開始時 `word_1D311` 歸零。
`word_1D313` 是等待計數器——**指令可以要求停幾幀**，這是動畫的節拍來源。

19 個指令的處理常式在 `sub_1A48C`–`sub_1A6E8`，都很短。
**還沒逐一解讀。**

## 4. ⭐ 戰場的資料模型

### 4.1 三層結構

```
BATTLE.MAP  512 B 索引（每筆 2 B）＋ 214 個戰場 × 4,096 B
              每個戰場：64 B 表頭 ＋ 3,968 格（64 × 62）＋ 64 B 尾段
              每一格 ＝ 一個 byte 的**圖塊編號**

BATTLE.MDL  4,096 B 表頭（3 × 256 B 屬性表）＋ 3 個圖塊組 × 63,488 B
              每組前 2,048 B ＝ 256 筆 × 8 B 的**圖塊定義**
              其餘 61,440 B ＝ 像素資料
```

索引的第一欄是圖塊組編號（0–2），第二欄見 §4.4。

### 4.2 ⭐ 一格是一疊圖塊，不是一塊

8 byte 的圖塊定義：

```
[0]        堆疊高度 k（0–7）
[1..k]     由下往上的子圖塊編號
[k+1..7]   0
```

驗過三個圖塊組共 768 筆：**`[k+1..7]` 全為 0，零例外**。
`[1..k]` 之間允許有 0（那一層是空的）。

兩支程式各自印證：

```asm
; sub_19E10：讀「最上層」那一格
mov ah, [bx]        ; 高度 k
add bl, ah
mov al, [bx]        ; ★ [k] ＝ 頂端的子圖塊
sub al, 0BAh / cmp al, 6 / jnb skip    ; 0xBA–0xBF → 生成一個物件

; sub_1BB6D：把七層各自的通行性寫進 7 張 4,096 B 的圖
mov ah, 7
.loop:
  inc bx / mov al, [bx]
  and al, al / jz .block
  cmp al, 70h / jnb .block             ; ★ 0 或 ≥ 0x70 → 該層不可通行
  and byte ptr es:[di], 7Fh / jmp .next
.block: or byte ptr es:[di], 80h
.next: add di, 1000h / dec ah / jnz .loop
sub di, 7000h
```

7 × 4,096 ＝ 28,672 ＝ `ds:0D2FA` 的大小，**完全吻合**。

### 4.3 ⭐ 堆疊高度 ≥ 4 ＝ 站在高處

```asm
; sub_1B240：單位移動後
mov ds, cs:word_1D2F6 / mov bl, [bx]   ; 該格的圖塊編號
cmp bl, 0F0h / jnb .clear
mov ds, cs:word_1D302
shl bx,1 ×3 / mov al, [bx]             ; 堆疊高度
cmp al, 4 / jb .clear
or byte ptr [si], 2                    ; ★ 單位旗標 bit 1
.clear: and byte ptr [si], 0FDh
```

把 214 張戰場依「堆疊高度 ≥ 4」上色，形狀自己說話
（`tools/battlefield.py map 5`）：

```
戰場 5（攻城用）                                戰場 200（野戰・平原＋水域）
 8 .........................OO########OOO######.   ............................
11 .........................###.................   ............................
25 .........................#####...............   ............................
52 .........................######################  ............................
```

**攻城用的戰場長出一圈封閉的城牆。** 這比「看圖塊像什麼」硬得多——
空間關係不是判讀時能安排的。

不過**高處不等於城牆**：野戰用的戰場也有高處，那是山與林。
下一節那張查表給了獨立的佐證。

### 4.4 ⭐ 野戰戰場是依地形組合查表選的

`sub_14BDD` 拿**兩格的地形類型**去查一張 21 筆 × 3 B 的表
（`cs:97F0h`，檔案偏移 `0x99F0`）：

```asm
mov bx, 97F0h / mov cx, 15h        ; 21 筆
.loop:
  mov dl, [bx]
  cmp ax, [bx+1] / jz .hit         ; (類型A, 類型B) 配對
  xchg al, ah / xor dh, 40h        ; ★ 換順序再比一次
  jnz .loop
  add bx, 3 / loop .loop
mov dl, 6                          ; 都不中 → 偏移 6
.hit: mov cx, dx / add cl, 0C0h    ; 戰場編號 ＝ 0xC0 + 偏移
```

⭐ **旋轉旗標就是「配對是換過順序才中的」**：`xor dh, 40h` 設的正是
`byte_10D35` 的 bit 6，而 `sub_1CAEB` 看的也是同一個位元。
戰場轉不轉 180 度，取決於兩格地形誰在前——不是另外算的方向。

地形類型的編號見 `docs/mechanics/30-combat.md` §2
（0 平原、3 山地、4／5 兩種林地、6／7 水域）：

| 戰場 | 地形組合 | 高處格數 |
|---:|---|---:|
| **192** | 山 ＋ 山 | **596** |
| 193 | 山 ＋ 平原 | 284 |
| 194 | 山 ＋ 林5 | 678 |
| 195 | 山 ＋ 水6 | 283 |
| 196 | 山 ＋ 林4 | 247 |
| 197 | 山 ＋ 水7 | 488 |
| **198** | 平原 ＋ 平原、平原 ＋ 林4、平原 ＋ 水7，**以及所有不中的組合** | **10** |
| 199 | 平原 ＋ 林5 | 208 |
| 200 | 平原 ＋ 水6、林5 ＋ 水6 | **0** |
| 201 | 林5 ＋ 林5、林5 ＋ 水7 | 344 |
| 202 | 林5 ＋ 林4 | 103 |
| 203 | 林4 ＋ 林4、林4 ＋ 水7 | **0** |
| 204 | 林4 ＋ 水6 | **0** |
| 205 | 水6 ＋ 水6 | 8 |
| 206 | 水7 ＋ 水7、水6 ＋ 水7 | **0** |

**高處格數是獨立算出來的，沒有進查表。** 而「山 ＋ 山」最多、
「平原 ＋ 平原」幾乎是平的、水與林的組合是零——
兩份互不相干的資料對上了，這張表的判讀可以定案。

另外七張走另一條路：`cl = 地形類型 + 0xCE`，也就是
**207–213 ＝ 地形類型 1–7**（跨水構造、山地、兩種林地、兩種水域）。
`sub_14C1A` 還會在地形類型 8 時從 209–212 隨機挑一張、類型 9 時固定用 213，
所以這五張有兩條來路。

### 4.5 索引第二欄是城門附近的 X 座標

`sub_1CAEB` 把它讀進 `byte_1AB4F`，而戰場旋轉 180 度時：

```asm
test cs:byte_10D35, 40h / jz skip
cmp cs:byte_1AB4F, 0 / jz .1
mov al, 3Fh / sub al, cs:byte_1AB4F    ; ★ v ← 63 − v
```

`0x3F` ＝ 63 ＝ **寬度 − 1**（戰場是 64 寬 62 高），所以它是 **X 座標**，
不是 Y。統計對得上（`tools/battlefield.py survey`）：

| 檢查 | 結果 |
|---|---|
| 戰場 **192–213**（野戰用）第二欄 | **全為 0**，22 張零例外 |
| 第二欄非 0 的 186 張 | **全部有高處**，零例外 |
| 第二欄 vs 最近的物件格 X | 25 張相同、123 張差 1、29 張差 2 |

戰場 0–191 一一對應 192 個據點——**`docs/re/05`「據點編號直接當戰場編號」
在資料上也成立了**。

### 4.6 物件格：頂層子圖塊 `0xBA`–`0xBF`

`sub_19E10` 掃過全部 3,968 格，替頂層落在這個範圍的格子各生成一個
32 byte 的記錄：

```asm
mov word ptr es:[di], 3C0h
mov es:[di+6], cl / mov es:[di+8], ch     ; X, Y
mov es:[di+0Ah], ah                       ; 堆疊高度
mov dx, 150h
test al, 1 / jz .1 / mov dx, 204h         ; 依子圖塊編號的奇偶二選一
.1: mov es:[di+1Ch], dx
call sub_1ECE0 / and al,3
mov es:[di+1Bh], al                       ; 隨機 0–3
add di, 20h                               ; 記錄 32 B
```

在攻城用的戰場上，這些格子**全部落在城牆線上**：戰場 5 是左牆面
兩段各 4 格、上下牆面各 5 格。說明書 4.4 說「梯子的位置每張地圖是固定的」，
位置對得起來。

⚠ **但不能就這樣定案。** 戰場 209–213（山地、林地、水域）上也各有
19–48 個物件格，而那裡沒有城牆。所以這個範圍是「**會生成互動物件的
子圖塊**」，城門與梯子只是其中一種用途。**用途待驗。**

野戰用的 192–208 一個物件格都沒有。

## 5. 還沒解的

按「解開之後能換到什麼」排序：

| 缺口 | 位置 | 換到什麼 |
|---|---|---|
| **19 個腳本指令** | `sub_1A48C`–`sub_1A6E8`，每個都很短 | 動畫與節拍怎麼驅動 |
| **單位記錄的欄位** | `ds:0D30E`（18,432 B），`sub_1B240` 用 `si` 掃 | 兵的狀態：位置、疲勞、士氣、命令 |
| **每幀更新** | `loc_1A065` → `sub_1A12A`／`sub_1A6FA`／`sub_1B941` | 移動、攻擊、判定的主體 |
| **六個戰術指令** | 左鍵 `sub_1BFF2`／右鍵 `sub_1C01D` | 突擊／攻擊／陣形／城壁／守陣／退卻 |
| **16 種陣形表** | 說明書 4.3 說有 16 種 | 陣形的相對座標 |
| **勝負判定** | 找 `mov sp, cs:word_1D340` | 「先補不出兵的一方輸」怎麼實作 |
| **物件格 `0xBA`–`0xBF` 是什麼** | `sub_19E10` 生成的 32 B 記錄，`+0x1C` 是 `0x150`／`0x204` | 城門、梯子還是別的 |
| 像素格式 | `BATTLE.MDL` 每組後 61,440 B（前 2,048 B 是圖塊定義） | 能把戰場畫出來 |
| `ds:0D2FC`／`0D2FE`／`0D300`／`0D306` | 合計 65,536 B | — |

**像素格式那一條特別值得先做**：戰場的形狀已經可以用堆疊高度畫出來
（§4.3 的 ASCII 圖就是），把像素解開就能直接和原版截圖比對，
而那是驗證其餘所有推論最便宜的辦法。
