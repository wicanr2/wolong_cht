- 範圍：只量松崗 DOS/V。PC-98 未納入

## 1. 這份文件回答什麼

`docs/re/20` 判斷「逆向夠不夠」的方法是挑出戰術相關函式逐一評估深度，
得到一組風險百分比。那份審計的問題不在結論，在**取樣**：手挑的函式清單
只能評估被挑到的那些，挑不到的函式連進入視野的機會都沒有。

這份改成全量量測——枚舉資料庫裡每一支函式，逐支問「專案有沒有任何一個檔案
提過它」。答案是可重跑的表，不是印象。

分級只看**證據在哪**，不看結論對不對：

| 分級 | 判準 |
|---|---|
| T1 | `docs/re/` 有寫（反組譯筆記層級） |
| T2 | `docs/` 其他地方有寫（格式、機制、playtest） |
| T3 | 只出現在狀態檔或程式碼（`CONTEXT.md`、`internal/`…） |
| T4 | 全專案沒有任何一處提過 |

**T3 要當心**：狀態檔提過不代表讀懂了。**T1 也不保證正確**——
它只保證有人寫過，正確性由那份文件自己的推論等級負責。

## 2. 方法：對唯讀副本跑，原始資料庫的身分才穩定

`idat` 一開啟 `.i64` 就會改寫它，雜湊跟著變。而筆記要靠雜湊標明
「這個結論是在哪一份資料庫上驗的」，資料庫身分會漂就失去意義。

`tools/ida.sh script` 因此先把 `.i64` 複製到 `workplace/ida/<版本>/census/`
再跑，並在前後各印一次原始檔雜湊。本次兩次都是 `7b7c…34c26`。

`docs/re/20` §2.1 記錄的「重新分析後枚舉出 739 支」在本次重現：
普查同樣得到 **739 支函式、50,586 bytes、22,267 個 instruction head**。
較舊文件寫的 732 支是另一次分析狀態的結果。
**函式數不是二進位身分，也不是完成率**——引用時要連同雜湊與工具版本一起寫。

### 4.1 戰術呈現是覆蓋率最高的模組，不是最低的

35 支函式裡 31 支有文件，T4 只有 2 支共 82 bytes。

這與 `docs/re/20` 給戰術相機／合成的 25–40% **不衝突，因為兩者量的不是同一件事**。
那份量的是「原版管線被移植進 remake 的程度」，這份量的是「函式有沒有被讀過」。
`docs/re/20` §3.2 自己就寫著「原版關鍵函式已定位，但 renderer 沒有按該管線實作」——
**定位 ≠ 移植**，兩份數字各自成立。

實務結論：戰術呈現的下一步是**照已解的管線改 renderer**，不是再開 IDA 找函式。
`docs/re/20` §5 的四個 gate 仍然適用，其中「重建原版 renderer IR」與「移植相機狀態機」
已在該文件 §7、§8 動工。

### 4.2 真正的缺口在戰略側

戰略 UI 82 支未觸及、月結／經濟／AI 72 支未觸及，兩者合計 9,940 bytes，
接近全部 T4 程式碼的一半。這兩塊在此之前沒有被任何一份稽核點名。

月結／經濟／AI 這一塊尤其值得注意：`CLAUDE.md` §6 把 `70-ai.md` 標成
優先度最高，而 `docs/mechanics/70-ai.md` 確實對**個別決策的判定式**寫得很細。
缺的是**骨架**——玩家怎麼走到那些決策、指令怎麼分派。
具體解法見 [`22-strategy-command-tree.md`](22-strategy-command-tree.md)。

## 6. 呼叫圖幾乎完整，所以 T4 不是死碼

739 支裡只有 **1 支**沒有任何直接呼叫者（`sub_14A0F`，108 bytes，訊息模組）。
其餘每一支都在直接呼叫圖上連得到。

這排除了「T4 是編譯器帶進來但用不到的程式庫」這個解釋——
**那 355 支是會被執行的遊戲程式碼，只是沒人讀過。**

`sub_14A0F` 的零呼叫者不等於死碼：直接 xref 抓不到間接分派與取址後呼叫。
它要嘛由某張跳表選中、要嘛被取址後間接呼叫、要嘛真的沒用到，三者要分開驗證。

## 7. 30 個間接呼叫點是靜態分析的斷點

`call cs:funcs_XXXX[bx]` 這種形式，IDA 看得到呼叫點卻不知道 runtime 選哪支，
呼叫圖在此斷開。30 處分佈在 29 支函式，其中 **19 處落在 T4 函式裡**。

但**表本身是靜態資料**。把表讀出來，候選集合就從「未知」變成「有界的清單」——
`tools/ida_dispatch_tables.idc` 做的就是這件事。這不等於知道 runtime 走哪條；
它把問題從「不知道有哪些可能」降級成「知道有哪些可能，還要驗哪一條會走到」。
兩者的推論等級不同，引用時不能混。

已攤開並定案的表見 [`22`](22-strategy-command-tree.md)。仍未攤開的：

| 所在函式 | 位址 | 指令 | 分級 |
|---|---|---|---|
| `sub_103E6`／`sub_1054D`／`sub_1059B` | `10401`／`10592`／`105E4` | `call cs:word_1036D` | T4 |
| `sub_15FAA` | `15FDC` | `call word ptr [bx+6056h]` | T4 |
| `sub_1E9C1` | `1E9F9` | `call word ptr [bx-15F3h]` | T4 |
| `sub_1ACD6` | `1ACF6` | `call cs:funcs_1ACF6[di]` | T3 |
| `sub_1BFF2` | `1C006` | `call word ptr [bx-3FB8h]` | T1 |

`word_181A6`／`word_181A8` 這一組**已解，靜態就夠**（見
[`26-list-window-engine.md`](26-list-window-engine.md) §3.1）：
它們是一覽表引擎的 callback 槽，八個呼叫端在進入 `sub_1820E` 時
用立即值把自己的 callback 位址傳進來，所以候選集合有限且已知。

靜態影像裡它們指向 `07 1F C3 90`（`pop es; pop ds; retn; nop`）確實是 return stub，
但那只說明**初值**是安全預設，不代表目標不可解。

**規則**：看到「全域函式指標」不要先判定要動態 trace。**先找誰寫它**——
寫入端如果是立即值，靜態就能把候選集合封口。

## 8. 怎麼重跑

```sh
tools/ida.sh script dosv tools/ida_function_census.idc KI.EXE.i64
tools/py.sh tools/re_coverage.py workplace/ida/dosv/census/census.tsv
```

第一步對 `.i64` 的唯讀副本跑，輸出 `workplace/ida/dosv/census/census.tsv`；
第二步掃 `docs/`、`internal/`、`cmd/`、`tools/` 與根目錄的狀態檔做交叉比對。
兩步都在容器內，`workplace/` 已 gitignore。

覆蓋率會隨文件增加而變動，**這份文件裡的數字是 2026-08-13 的快照**。
要現況一律重跑，不要引用這裡的百分比。
