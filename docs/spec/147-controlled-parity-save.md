# 147 — 受控存檔：把會動的東西先關掉，長時間對拍才有意義

**狀態：CONFORMED。** 即時制的逐像素對拍最怕「兩邊各自擲骰」。
`tools/parity_save.py` 從既有的 `SAVE.DAT` 出發、只改指定欄位，
做出一份**兩邊都載得進去的受控存檔**。第一個改法是
`--no-clouds`：把大地圖上那 16 朵會飄的雲停用。
效果是**跑滿一個遊戲日之後，`map` 的殘差從 11,420 px 掉到 66 px**，
而那 66 px 是原版自己畫的地圖游標框。

- 日期：2026-09-06
- 出處：`sub_12459`／`sub_12533` 都以 `cmp byte ptr [si], 80h / jb` 跳過
  停用的物件槽（[`146`](146-map-cloud-objects.md) §2）
- 推論等級：**confirmed**（dosgolem 實測：載入後座標與計時器一動也沒動）
- 驗證：[`../playtest/88`](../playtest/88-controlled-save-parity.md)
- 相關：[`90`](90-same-state-parity.md)（同狀態對拍）、
  [`118`](118-shot-when-condition.md)（取樣點）

## 1. 問題

`docs/spec/90` 的同狀態對拍靠「兩邊載同一份存檔」建立起點，
但**起點相同不代表軌跡相同**：天災、雲的漂移、AI 的判斷都吃亂數，
而兩邊的亂數流不是同一條。取樣點一拉長，畫面上就會出現
「原版的雲」與「remake 的雲」兩片，殘差**加倍**——
那不是規則分歧，是亂數分歧（[`../playtest/87`](../playtest/87-map-clouds.md) §5）。

⭐ **改狀態比等亂數可靠。** 把會動的東西先關掉，剩下的差異才有意義。
這也是 `CLAUDE.md` §3.1 講的「靠存檔而不是操作序列定位狀態」再往前一步：
**存檔本身也可以是實驗器材**。

## 2. `--no-clouds` 怎麼做到的

物件記錄的 `+0x00` bit 7 是存在旗標。原版的兩支消費端都先看它：

```asm
sub_12459:  cmp byte ptr [si], 80h / jb 跳過   ; 不推進、不移動
sub_12533:  cmp byte ptr [si], 80h / jb 跳過   ; 不繪製
```

所以把後 16 槽（區塊位移 `0x21C0` 起，每筆 16 B）的 bit 7 清掉，
就等於整個關掉。**dosgolem 實測**：載入受控存檔跑到 196/4/21，
`peek:2754:2140:48` 讀回

```
00 00 F3 FF 0E 01 00 00 F7 FC F2 00 0C 10 00 00
└ 旗標 0    └ 座標與計時器與檔案裡一模一樣
```

——旗標清掉了，**座標與計時器一動也沒動**，證實那兩支真的整筆跳過。

## 3. 用法

```sh
tools/py.sh tools/parity_save.py <來源 SAVE.DAT> <輸出目錄> --no-clouds
tools/py.sh tools/parity_save.py --selftest
```

輸出只有 `SAVE.DAT`；**dosgolem 的 gamedir 要自己備妥其餘原版檔案**。
這一支不碰來源、不碰 `workplace/orig/`。

⚠ **自我測試要有負對照**：`--selftest` 除了驗「16 朵都關掉、前 16 槽沒被動到」，
還驗「空區塊回 0 朵」與「只動指定的區塊」。
少了負對照，一支「什麼都沒改」的工具也會通過。

## 4. 效果

鏡頭 (271,153)、從 196/4/20 跑到 4/21 11 時（**一整個遊戲日**）：

| 存檔 | `banner` | `command` | `map` | `minimap` | `faction` |
|---|---:|---:|---:|---:|---:|
| 原本的（雲各自漂）| 0 | 0 | 22,210 | 0 | 0 |
| **`--no-clouds`** | **0** | **0** | **66** | **0** | **0** |

那 66 px 是**原版畫在地圖上的游標框**（白色空心 16×16），
剛好落在鏡頭跳過去的那一格上——remake 沒有這個框（§5）。

## 5. 注入原版的亂數狀態

`--no-clouds` 繞開了雲，但**內政本身也吃亂數**——`sub_14194` 的每一次
整備都取一個 byte（remake 是 `governor.Tick` 的 `rng.Next()`）。
兩邊各自擲骰，跑一個遊戲日之後據點一覽的上昇率就差到 ±4
（[`../playtest/89`](../playtest/89-advise-status-parity.md) §3）。

⭐ **那條流是可以搬過來的。** 原版的產生器 `sub_1ECE0` 全解在
[`../re/10`](../re/10-rng.md)，狀態只有三樣東西，而且都在固定位址：

| 位址 | 內容 |
|---|---|
| `cs:1ECFCh` | 計數器 `c` |
| `cs:1ECFDh` | 狀態 `s` |
| `cs:1ECFEh` 起 256 B | 置換表 `T` |

所以 **`ipeek:1ECFC:258` 一次就把整個產生器讀出來**，
`-rng-state <檔>` 再灌進 remake，兩邊的亂數流從那一刻起完全相同。

⚠ **量過了：搬過去沒有變好，反而更差**（286 → 421 px，
[`../playtest/89`](../playtest/89-advise-status-parity.md) §4）。
機制本身沒問題——單測證明兩邊吐出同一串數；壞的是**消費順序**：
兩邊在同一拍取的亂數個數不同，序列從第一個不一致的地方就岔開，
之後只是**換一種岔法**。

⭐ **所以這個機制目前的用途不是「讓對拍變準」，是把岔開的位置變成
看得到的東西。** 真正要做的下一步是逐拍數兩邊各取幾個亂數。

⭐ 同一輪量到一個更實用的結論：**經過時間才是主因**。同一條流程
在載入後 4 個遊戲日取樣是 805 px、20 個遊戲小時是 286 px——
**含動態欄位的畫面要在載入之後盡快取樣**。

## 6. 未解

| 項目 | 現況 |
|---|---|
| **原版的地圖游標框** | 白色空心 16×16，貼著游標所在的格。remake 沒有畫；要接得先讀出它的顏色、線寬與更新時機（`sub_11F7F` 每圈算游標所在格）|
| 還能關掉什麼 | 目前只有 `--no-clouds`。天災、AI 出兵、募兵都吃亂數，各自需要自己的「關掉」欄位 |
| 兩邊的**消費順序**能不能對齊 | 狀態可以搬（§5），順序還沒逐拍比過 |
