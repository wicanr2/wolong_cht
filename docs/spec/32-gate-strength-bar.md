- 推論等級：confirmed

## 1. 原版做什麼

城壁或城門挨打時，**戰場區上緣**跳出「門強度」＋一條進度條，
顯示那個實體的剩餘耐久；20 幀之後自己收掉，右鍵也能提前收掉。

它不是常駐的 HUD——**不挨打就不存在**。

| 階段 | 位址 | 動作 |
|---|---|---|
| 建立 | `0001C43C`–`0001C479` | 清 (264,8)-(471,23)、註冊熱區 `0x1D` (256,0,224×32)、畫「門強度」於 (264,8) 色 15 |
| 更新 | `0001C47B`–`0001C495` | `[di+0x18] < word_1C405` 才更新最小值、重畫條，並把到期時刻設成 `word_1D318 + 0x14` |
| 收掉 | `sub_1C4A6` | `word_1D326 ← 0xFFFF`、清熱區與顯示旗標 |

**只在更小的值出現時重畫**，所以這條只會往下掉，不會回升——
即使之後打到的是另一段耐久更高的城壁。

## 2. 演算法

```
# 挨打時（每個實體各呼叫一次）
if 到期時刻 == 未設定:                 # word_1D326 == 0xFFFF
    建立版面
    已畫過的最小值 = 未設定             # word_1C405 ← 0xFFFF
if 實體耐久 < 已畫過的最小值:
    已畫過的最小值 = 實體耐久
    畫條(實體耐久)
    到期時刻 = 目前幀 + 0x14           # 20 幀

# 每幀
目前幀 += 1
if 目前幀 == 到期時刻: 收掉

# 畫條（sub_1C4D2 → sub_10AAA）
長 = 0
if 實體記錄[+0x00] >= 0x80:            # 這一格有實體（0x0180 城壁／0x0280 門）
    長 = min(耐久 >> 4, 0x97)
在 (320, 16) 畫 0x97 ＝ 151 px 長、2 px 高：
    前 長 px 用調色盤索引 11，其餘用索引 0
```

⭐ **這條其實從來不顯示門的耐久。** 呼叫端 `0001B601` 有兩道閘：

```asm
0001B601  cmp cs:byte_1D34B, 0 / jnz 出   ; 只有攻城戰
0001B609  cmp byte ptr [di+1], 1 / jnz 出 ; ★ 只有實體類型 1 ＝ 城壁
0001B60F  call sub_1C407
```

所以上限 151（對應耐久 2,416）是為**城壁**設計的——攻城的城壁耐久是
`(據點 +0x13 + 50) × 10`，動輒上千。門的耐久只有 80，但它根本走不到這裡。
標籤寫「門強度」而顯示的是城壁，**照抄，不要改名也不要改倍率**。

⚠ `word_1D318` 是 **byte**，會在 256 回繞；到期判定用的是**相等**不是「≥」。
remake 的幀計數不回繞，而每幀固定 +1，所以相等判定等價。

## 4. 驗證

| 方式 | 證據 |
|---|---|
| 單元測試（規則） | `TestStructureBarFollowsRawMinimumAndExpiry`、`TestStructureBarExpiresThroughStep`（`internal/rules/tactical`）|
| 單元測試（版面） | `TestGateBarGeometryMatchesRawConstants`（`cmd/wlgame`）。它同時釘住一件事：標籤的 x=264 正好是 TALK 框右緣 256 再 +8——**條不會被 TALK 蓋掉**，而這解釋了原版為什麼選 264 |
| 對原版 | [`../playtest/27`](../playtest/27-original-video-frame-parity.md) §7.5 的影片影格。**remake 側沒有截圖**——原因見下 |

⚠ **沒有 remake 截圖不是漏做。** 這條只在實體挨打後亮 `0x14` 幀；
拿真實 `BATTLE.MAP` 的攻城圖跑 2,000 幀量過，**只亮了 21 幀（1.1%）**，
而且集中在第 24–44 幀。單張截圖抓到的機率太低，
不值得用每張 40 秒的 Xvfb 迴圈去碰運氣。
