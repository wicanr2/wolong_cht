# 160 — 亂數消費順序對齊：逐次比「誰取了第幾個數」

**狀態：DRAFT。** 原版側的軌跡已經取得（§2 實測），remake 側的軌跡與
比對工具還沒做。**這一份是長時間對拍的前置**——順序沒對齊之前，
逐點差異裡的亂數噪音與真規則分歧分不開。

- 日期：2026-09-09
- 出處：`KI.EXE` `sub_1ECE0`（`0001ECE0`）是取數的唯一入口
  （[`../re/10`](../re/10-rng.md) §1）；remake 對應
  `internal/rules/rng.Rand.Next`
- 推論等級：產生器本身 confirmed（兩邊單測吐出同一串數）；
  **消費順序未知**，這一份定的是怎麼把它量出來
- 相關：[`147`](147-controlled-parity-save.md) §5（狀態搬得過去、順序沒對齊）、
  [`138`](138-state-table-parity.md)（狀態表逐欄比）、
  [`139`](139-ai-decision-trace.md)（事件軌跡）

## 1. 問題

[`147`](147-controlled-parity-save.md) §5 把原版的產生器狀態
（`ipeek:1ECFC:258` 的 258 byte）灌進 remake 之後，同一條流程的殘差
**從 286 px 變成 421 px**。產生器沒有錯——壞的是消費：兩邊在同一拍
取的亂數個數不同，序列從第一個不一致的地方岔開，注入只是換一種岔法。

所以「兩邊 seed 一致」目前是做不到的事，而不是設定問題。要做到，
得先知道**兩邊各在什麼時候、由哪一支函式、取了第幾個數**。

## 2. 原版側：`-watch 1ECE0` 一次呼叫一行

```sh
WOLONG_DOSGOLEM_GAMEDIR=dosgolem/root-noclouds \
WOLONG_DOSGOLEM_WATCH=1ECE0 \
WOLONG_DOSGOLEM_BUDGET=200000000 \
tools/dosgolem.sh <out> "wait;click:320,200;click:300,151;clock;until:196/4/18;clock"
```

每次呼叫印一行，**指令序號、暫存器、呼叫端**都在：

```
  #16735858 呼叫 1ECE0 AX=5500 BX=0030 CX=0108 DX=0104 SI=0EA0 DI=7D00 來自 近=141D8 遠=526A8
```

⭐ **`來自 近=` 那一欄是這份規格的核心。** 它把「第幾個亂數」變成
「哪一支函式取的第幾個亂數」——兩邊比對的時候，第一個不一致的
呼叫端直接指出是哪一條規則多取或少取，不必從像素反推。

### 2.1 閒置期的消費端只有四個位址

`root-noclouds`（196/4/16 13 時起）推到 196/4/18 1 時，36 個遊戲小時：

| 呼叫端 | 次數 | 所屬 |
|---|---:|---|
| `141D8` | 330 | `sub_14194` 內政官整備（[`../re/07`](../re/07-monthly-settlement.md) §20）|
| `141F1` | 330 | 同上 |
| `14216` | 322 | 同上 |
| `14060` | 12 | `sub_13EFD` 底下（[`../re/38`](../re/38-strategy-core-module-map.md)）|

前三個成組出現，每 24,900 道指令（＝一個子刻，
[`../playtest/65`](../playtest/65-dosgolem-oracle.md) §5）一組三次。
一個遊戲日 216 子刻 ⇒ **約 648 次／日**，一個遊戲月約兩萬次、2 MB。

⚠ 這是**閒置期**的數字。開戰、天災、募兵、攻城各有自己的消費端，
清單會變長——所以判準不能寫死成「四個位址」，要逐輪重新統計。

## 3. remake 側：在唯一入口記同樣的東西

`internal/rules/rng.Rand.Next` 是 remake 取數的唯一入口，加一層可關閉的
軌跡：序號、呼叫點、回傳值、當下的遊戲時刻。呼叫點取 `runtime.Caller`
的檔案與行號——它對應原版的 `來自 近=`，是兩邊唯一能對得起來的東西。

軌跡預設關閉：長跑時每次取數多一次 `runtime.Caller` 會拖慢規則層，
而規則層在 `wlsim` 底下是要跑幾年的。

## 4. 判準：以遊戲小時分段，段內比呼叫端序列

兩邊的時間軸單位不同（原版是指令序號，remake 是 tick），
**共同的錨點只有遊戲時鐘**。所以比對是兩層：

| 層 | 比什麼 | 不一致代表 |
|---|---|---|
| 段 | 每個遊戲小時各取了幾個數 | 某一支規則多跑或少跑 |
| 段內 | 呼叫端的**序列**（不是集合）| 順序不同——同樣的規則跑了，但先後不同 |

⭐ **第一個不一致的段就是唯一要看的地方。** 之後的所有差異都是它的
下游，逐段列出來只會讓真正的分歧埋在噪音裡。

⚠ **對齊的目標不是「讓數字一樣」。** 兩邊取一樣多的亂數只是必要條件；
真正要問的是「為什麼原版在這一刻取三個而 remake 取兩個」，
答案永遠是一條沒接上或接錯的規則。

## 6. 驗證

1. 兩邊各跑同一條時間軸（同一份受控存檔、同一個 `-rng-state`），
   各產出一份軌跡。
2. 比對工具印出**第一個不一致的遊戲小時**與該段兩邊的呼叫端序列。
3. 每修掉一條分歧，回跑同一條時間軸，第一個不一致的時刻要往後推。
   **往後推的幅度就是進度**，這是這條長期工作唯一不會自我安慰的指標。
