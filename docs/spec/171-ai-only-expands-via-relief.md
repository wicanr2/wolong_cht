# 171 — AI 擴軍的唯一入口是**據點求援**，不是每拍每據點

**活軍團數與原版完全相同**（8／8／8／10），據點表與武將表逐 byte 相同。

## 1. 原版只有一條鏈

把四支編成常式的呼叫端全部列出來：

| 常式 | 誰呼叫 | 是什麼 |
|---|---|---|
| `sub_14575` | **`sub_140C9` 一處** | 據點求援時的擴軍額度 |
| `sub_145C1` | `sub_14575` | 挑一名未出陣、`+0x11` 最高的武將 |
| `sub_16E8F` | `sub_145C1`、`sub_1699E` | 編成本體；後者是**君主親自出陣** |
| `sub_16F26` | `sub_16E8F`、`sub_16C92` | 建軍團記錄；後者是**玩家的編成畫面** |

⭐ **AI 自動擴軍只有 `sub_140C9` 那一條**，而 `sub_140C9` 只有兩個呼叫端
（`sub_14028`、`sub_14057`），都在據點求援裡。

`sub_13EFD`（每拍一個據點）做的是：求援冷卻 −1 → 易主記錄 → 佔用圖抄進
`+0x18` → `sub_13F74`（威脅與求援）→ `sub_14194`（內政）→ `sub_14269`（災害）。
**沒有編成入口。**

## 2. remake 現況

`internal/state/state.go` 的 `tickCity`：

```go
var aiEvent *StrategyEvent
if w.strategicAI && c.Owner >= 0 && c.Owner < numFactions && c.Owner != w.Player {
    aiEvent = w.formAICorps(c.Owner)   // ⚠ 每一拍、每一個非玩家的據點
}
```

`formAICorps` 的閘只有「有侵攻目標 ∧ 軍團額度 > 0 ∧ 有閒置武將 ∧ 預備兵夠」，
所以只要額度沒滿就幾乎每拍編一支，直到 `max(5, 資金 ÷ 8192)` 用完。

## 3. 量到的差

同一份快照、同一條亂數流：

| | 活著的軍團數（原版 / remake）|
|---|---|
| 起點 | 8 / 8 |
| 拍 200 | **8 / 20** |
| 拍 700 | 8 / 21 |
| 拍 1,200 | 8 / 16 |
| 拍 1,900 | 10 / 16 |

⭐ 原版在 1,900 拍（約 9 個遊戲日）只多編了 **2 支**。

下游跟著全歪：自動判定戰鬥的取數原版 168、remake 396；
勢力記錄 `+0x04`–`+0x09`（預備兵）與據點 `+0x13`（城兵）大量不同——
編一支軍團要抽預備兵，而預備兵來自徵兵。

## 4. remake 要改什麼

拿掉 `tickCity` 裡那一次呼叫。AI 擴軍改為只走求援那條鏈
（`relieve` → `requestRelief` → `formAICorpsTo`），與 [`164`](164-relief-request-gates.md) 一致。

`formAICorps(faction)`（`dest < 0`，目標由侵攻對象決定）在 `internal/` 就沒有
呼叫端了，只剩 `ai_probe_test.go` 用它驗閘——保留函式，並在註解寫明
**它不是每拍的入口**。

## 5. 怎麼驗

1. 同局面對拍：拍 200／700／1,200 的活軍團數要回到 8。
2. 據點 `+0x13`（城兵）與勢力 `+0x04`–`+0x09`（預備兵）的差異要大幅下降。
3. `internal/state` 既有測試維持綠燈（`ai_probe_test.go` 直接呼叫該函式，不受影響）。

## 6. 改完之後量到的
