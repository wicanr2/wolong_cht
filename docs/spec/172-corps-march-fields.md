# 172 — 補齊軍團行軍的五個欄位：`+0x0A`／`+0x0C`／`+0x0E`／`+0x1A`／`+0x1C`

**狀態：CONFORMED。** 五個欄位都接上了；建表序號與原版連結記錄
**254/254 同序**，同局面對拍的軍團表在拍 200／700／1,200 都只剩 `+0x00`
一個未建模的旗標位元（據點表與武將表四個檢查點逐 byte 相同）。
載入存檔時的行軍還原與手動擺位的路徑作廢也在裡面（§4.5、§4.6）。

## 1. 還差哪些

同局面對拍的四張表裡，只剩軍團還有差，而且**全部集中在行軍狀態**：

| 偏移 | 內容 | remake 現況 |
|---|---|---|
| `+0x0A` | **沿路徑表前進的步進量**（`+4` 正向、`0xFC` ＝ −4 反向）| 沒建模 |
| `+0x0C` | **路徑表指標**（段內位址，每筆 4 B）| 沒建模 |
| `+0x0E` | 現在節點：**據點 × 8**（`< 0x600`）或**連結記錄的位址**（`≥ 0x800`）| 只放據點 × 8 |
| `+0x1A` | 佔用圖的段內偏移 ＝ 現在的 X | 沒維護 |
| `+0x1C` | 佔用圖的段位址 ＝ `word_19872 ＋ Y × 24` | 沒維護 |

`+0x1A`／`+0x1C` 是純導出值（X 與 Y 的另一種寫法），`+0x0A`／`+0x0C`／`+0x0E`
則要有一張與原版**同構且同位址**的道路表才寫得出來。

## 2. 前提：路徑已經逐格相同

[`169`](169-march-has-no-city-stub.md) 已經驗過：remake 的 254 條邊與原版
執行期建的表**整條逐格相同**。所以缺的不是路徑本身，是**表的位址版面**。

原版的版面（[`../re/08`](../re/08-hourly-update.md) §7.1–§7.3）：

```
0x0000–      索引表     每個據點節點 8 B，+6／+8 指向兩個方向的連結記錄
0x0800–      連結記錄   16 B：+00 第一筆路徑點、+02 最後一筆、+04 點數（不含最後）、
                              +06／+08 兩端節點、+0A–+0E 外接矩形
0x2000–      路徑點     4 B：X（word）、Y（byte）、旗標（`44` 起點／`04` 終端）
```

⇒ 第 `k` 筆連結記錄在 `0x800 + k × 16`，它的路徑點從 `0x2000` 起**依序接排**。
**只要邊的順序與原版一致，整張表的位址就完全決定了。**

## 3. 順序：建表序號 254/254 對上

remake 的 `RoadEdges` 最後照 `(A, B)` **排序**，原版是**建表順序**
（逐據點、逐方向 walk，先建先得）。兩者在「同一個據點的多條邊之間」不同：

```
原版   … 1→4  1→2  2→3 …
remake … 1→2  1→4  2→3 …
```

⇒ 排序輸出保留（那是既有行為），另外記下**建表序號** `Seq`
（`starts` 的走訪次序，先走到先得）。

實測 `Seq` 的順序與原版連結記錄 **254/254 完全相同**——走訪的方向枚舉
本來就與 `sub_1E57F` 一致，差的只是最後那一次排序。
⇒ 整張表的位址完全可重建：連結記錄 `0x800 + Seq × 16`、
路徑點從 `0x2000` 起依 `Seq` 累加 `(len(Path) − 1) × 4`。
（驗證：第 0 條 `0x2000`、15 點；第 1 條 `0x203C` ＝ `0x2000 + 15 × 4` ✓）

## 4. remake 要改什麼

**一、`internal/assets/world`**：`RoadEdge` 加 `Seq int`（建表序號，
`starts` 的走訪次序），輸出順序不變。

**二、`internal/rules/march`**：由 `Seq` 算出每條邊的
`LinkAddr = 0x800 + Seq × 16` 與 `PathAddr`（`0x2000` 起依 `Seq` 累加
`點數 × 4`）。這兩個值只給存檔寫回用，不進路由邏輯。

**三、`internal/state`**：`Corps` 加三個欄位

```go
// Step 是 +0x0A：沿路徑表前進的步進量（+4 正向、−4 反向）。
Step int
// PathPtr 是 +0x0C：路徑表指標（段內位址）。
PathPtr int
// LinkAddr 是 +0x0E 在**行軍中**的值：連結記錄的位址（≥ 0x800）。
// 停在據點上時 +0x0E 是據點編號 × 8，那一種由 Node 表示。
LinkAddr int
```

行軍時由 `w.step` 維護：踏出第一格時設 `LinkAddr`／`PathPtr`／`Step`，
每走一格 `PathPtr += Step`，到站時清回 0。

**四、寫回**（`saveCorps`）：`+0x0A`／`+0x0C` 直接寫；`+0x0E` 在
`LinkAddr != 0` 時寫 `LinkAddr`、否則寫 `Node × 8`；
`+0x1A` 寫 X、`+0x1C` 寫 `word_19872 + Y × 24`。

⚠ `word_19872` 是**執行期配置的段位址**（實測 `0x46B3`），不在存檔裡。
寫回時用載入來源的既有值當基底（`+0x1C` 減去 `Y × 24`），
沒有來源就跳過那一欄——**不要編一個段位址出來**。

## 4.5 ⚠ 載入存檔時要把行軍路徑接回來

實作時才發現的第六個缺口：`loadCorps` 讀回了 `+0x0A`／`+0x0C`／`+0x0E`，
但沒有**重建格子路徑**——於是「存檔時正在行軍」的軍團載入後走的是直線退路。

`+0x0E`（連結記錄位址）＋ `+0x0C`（路徑點位址）＋ `+0x0A`（步進方向）
**完整描述了軍團走在哪一條路的第幾格**，所以路徑重建得回來：

```go
a, b, ok := w.roads.EdgeByLink(c.LinkAddr)
from := a
if int8(c.Direction) < 0 { from = b }   // 0xFC ＝ 沿路徑表倒著走
cells, marks := w.roads.CellRouteMarked(from, c.TargetNode)
// 丟掉已經走過的前綴：對齊到存檔記的那個路徑點位址
```

⚠ 道路圖是呼叫端注入的，所以這件事只能掛在 `SetRoads` 上——
`loadCorps` 執行時還沒有圖。

## 4.6 手動擺位要把路徑一起丟掉

驗收捷徑（`internal/battlesetup` 的 `StageEncounter`）會**把軍團直接擺到
某一格**。座標一被外力改掉，`+0x0C`／`+0x0E` 描述的那條 leg 就不再是它
走的路，留著有兩個後果：沿舊路徑走回去，或者被 §4.5 的守衛
（有 `LinkAddr`、沒有格子路徑）當成「還原不了」而**整支凍住**。

⇒ `World.ClearMarchRoute(i)`：丟掉 `routes`／`routeMarks`，
把 `LinkAddr`／`PathPtr` 歸零。擺位的兩個分支各自對被搬動的那一支呼叫。

⚠ 這是守衛抓到的**第二個**既有缺口（第一個是
`TestFieldBattleTerminates` 根本沒接道路圖）。兩個症狀相同：
**在此之前它們靠直線退路碰巧撞得出遭遇**。

## 5. 怎麼驗

1. `Seq` 的順序與 `tools/orig_roadtable.py` 解出的連結記錄順序 **254/254 相同**。
2. 同局面對拍：軍團表在四個檢查點的差異欄位歸零。
3. `internal/assets/world`、`internal/rules/march`、`internal/state` 測試全綠。

## 5.5 量到的

| 檢查點 | 軍團表的差異 |
|---|---|
| 拍 200 | **`+0x00`（1 支）** |
| 拍 700 | **`+0x00`（1 支）** |
| 拍 1,200 | **`+0x00`（1 支）** |
| 拍 1,600 | `+0x00`（1 支）、`+0x08`／`+0x09`／`+0x0B`（2 支）|
| 拍 1,900 | 上列再加走位已經岔開的 2 支 |

`+0x00` 剩的是位元 0（未建模，見 §6）。據點表與武將表在四個檢查點
**逐 byte 相同**，勢力表只剩資金。

比對工具是 `tools/corps_diff.py`——⭐ **只比兩邊都活著的軍團**：
一支只在單邊存在時整筆 64 byte 都會不同，那是「編成時機不同」不是
「欄位對不上」，混在一起看會把後者淹掉。
