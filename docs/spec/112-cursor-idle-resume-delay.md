# 112 — 游標停下之後的恢復延遲

**狀態：CONFORMED。** 原版在「游標移動中」與「游標剛停下的 0.549 秒內」
都不推進世界。remake 已有前半（座標比對），缺後半（恢復延遲）。

- 日期：2026-09-02
- 出處：`KI.EXE`（SHA-256 `fffeba98…d43868`）的 `sub_11F7F`（`0001204D` 一帶的
  `mov byte ptr ds:98A5h, 0Ch`）、`sub_18810+37`（`mov cs:byte_198A5, 8`）、
  `sub_11CD0`（`00011CD0`–`00011D0B` 的三條路）；回呼頻率見
  [`../re/61`](../re/61-timer-tick-source.md) §3、機制整理見同文件 §5.1
- 推論等級：**confirmed（靜態）**
- 為什麼要有：**這是即時制底下給玩家的反應時間**（使用者裁定 2026-09-02）。
  沒有它，光是把游標移到指令列上、再移到目標據點，時間就已經走掉，
  玩家來不及把一條命令下完。

## 1. 原版做什麼

`ds:98A5h` 是一個以時鐘回呼為單位的倒數。三條路（`sub_11CD0`）：

| 值 | 行為 |
|---|---|
| `> 1` | `ds:0D2Ch`／`ds:0D2Dh` 歸零、遞減，**直接 `retn`** |
| `== 1` | `ds:0D2Dh` 沒累積到 `0A0h` 就 `retn`；到了才 `sub_20000(ax=2)`、三個變數歸零，落到正常路 |
| `== 0` | 正常路：`sub_13EFD`（據點每 tick）、`sub_125A3`… |

前兩條都跳過 `sub_13EFD`，所以那段時間**世界不前進**。

寫入端兩處，關鍵是第一處**只在座標有變化那一支**：

```asm
; sub_11F7F —— 讀到滑鼠座標之後
00011FB2  cmp cx, word_1987E / jnz loc_11FD0
00011FB8  cmp dx, word_19880 / jnz loc_11FD0
          …（座標沒變：什麼都不設，直接回）
loc_11FD0:
00011FD0  mov ds:987Eh, cx / mov ds:9880h, dx
00011FD8  mov byte ptr ds:98A5h, 0Ch        ; ★ 只有這裡

; sub_18810 —— 擦掉訊息框之後
          sub_1895D(al=0, dx=0Ah, bx=8, cx=510h)
          mov cs:byte_198A5, 8
```

⭐ **游標一直動就一直被重設回 12**，倒數永遠走不完 ⇒ **移動期間時間完全停住**。

## 2. 演算法

```
游標座標與上一幀不同，或這一幀有輸入 → 重設倒數，世界不動
否則                                → 倒數，走完才讓世界動
倒數長度 = 160 個回呼 ＝ 160 ÷ 291.30 Hz = 0.5493 秒
```

`0A0h` ＝ 160 是 `ds:0D2Dh` 的門檻，291.30 Hz 出自
[`../re/61`](../re/61-timer-tick-source.md) §3（PIT 4660.87 Hz ÷ 16）。

⚠ **`98A5h` 從 12 倒數到 1 的那 11 輪不另外模擬。** 它一輪 ＝ 一次主迴圈，
而原版主迴圈的速度**跟著機器跑**（`CLAUDE.md` §3.1），沒有可抄的數字；
0.549 秒那一段才是有定義的時間量。這是 **remake 差異**，寫在這裡。

## 3. remake 實作

換算用 `internal/rules/speed` 既有的定點單位（`UnitsPerFrame` ＝ 2913、
`Scale` ＝ 600，一幀 ＝ 4.855 個回呼），門檻就是 `160 × Scale`：

| 項目 | 位置 |
|---|---|
| 倒數本體 | `cmd/wlgame/idle.go` 的 `idleClockGate`：加一個中斷單位累加器 |
| 游標移動／輸入 → 重設 | 同上，`Allows` 既有的 `moved || inputActive` 那一支 |
| 訊息框收掉 → 重設 | `cmd/wlgame/messages.go` 的 `updateMessageOnly`，收掉一則時呼叫 `Pause()` |

⚠ **不要用「幀數」寫死。** 用 `speed` 的單位換算，速度層與這一層才會在
同一個時間基準上；直接寫 33 幀會在改幀率時默默漂掉。

### 3.1 ⭐ 哪些輸入會「重新等滿」，哪些只擋一 frame

**原版寫恢復倒數的只有一支：游標座標與上一次不同。** 按鍵不寫、
點滑鼠鍵也不寫。所以 remake 的輸入要分兩類，不能一律重新計時：

| remake 的輸入 | 原版對應 | 效果 |
|---|---|---|
| 滑鼠游標移動 | `sub_11F7F` 的 `loc_11FD0` | **重新等滿** |
| 方向鍵捲鏡頭 | 原版捲地圖**就是游標移動**——大地圖上 INT 33 的範圍是整個世界，`sub_11F7F` 把游標夾回 640×400 時**順手把鏡頭原點拉過去**（[`../re/47`](../re/47-main-screen-window-registry.md) §6）。所以捲動與移動是同一件事，走同一支 | **重新等滿** |
| 訊息框收掉 | `sub_18810` 的 `mov cs:byte_198A5, 8` | **重新等滿** |
| 滑鼠鍵按著 | 原版按鍵不寫 `ds:98A5h` | 只擋這一 frame |
| ＋−（調速度）| remake 自己加的鍵盤捷徑，原版沒有 | 只擋這一 frame |

⚠ **原版的戰略層完全沒有鍵盤**（[`../re/22`](../re/22-strategy-command-tree.md) §2）。
先前 remake 自己加的 `ESC` 與 `1`–`4` 已在 2026-09-02 移除
（使用者裁定，[`13`](13-main-window-toggles.md) §3）；`＋−` 還在，
所以「只擋一 frame」那一類仍然要有。

⚠ **這一格分錯會很難查。** 把命令輸入也算成「重新等滿」，效果是
**每按一次快捷鍵世界就凍半秒**——原版沒有這回事，而且症狀是
「遊戲時間好像走得比預期慢」，不會有人聯想到是鍵盤。

## 4. 驗證

| 方式 | 證據 |
|---|---|
| 單元測試 | `TestIdleClockGateHoldsWhileCursorMoves`、`TestIdleClockGateResumesAfterDelay`、`TestIdleClockGateScrollRestartsButCommandDoesNot`、`TestIdleClockGatePauseRestartsDelay`（`cmd/wlgame`）|
| 數字 | 門檻 `160 × 600 ＝ 96,000` 單位，每幀 `2,913` ⇒ **33 幀**（60 fps 下 0.550 秒，與原版 0.5493 秒差 0.1%）|

## 5. 未解

| 項目 | 現況 |
|---|---|
| `sub_20000(ax=2)` 為什麼在恢復時被呼叫 | 那是滑鼠層跳表的第 2 號（`sub_2009A`，回傳快取座標並清旗標），在這個時點叫它的理由沒讀 |
| 訊息框那一路的 `8` 與游標的 `0Ch` 為什麼不同 | 兩個立即值都是 confirmed，但差別的用意沒有證據；remake 兩邊都用同一個延遲 |
