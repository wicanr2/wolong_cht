## 1. 原版的順序

```asm
cmp byte [si+857h], 0 / jz +2 / dec byte [si+857h]   ; ① 求援冷卻 −1
bh = [si+85Ah] / cmp bh, [si+841h] / jz 跳過         ; ② 易主 → 原主勢力 +0x17
ax = [si+84Ah] × 24 + cs:word_19872 / es = ax
al = es:[bx] & 7Fh / [si+858h] = al                  ; ③ 佔用圖抄進 +0x18
cmp byte [si+841h], 18h / jz 跳過
  sub_13F74                                          ; ④ 威脅偵測 ＋ 求援
sub_14194 / sub_14269                                ; ⑤ 內政 ⑥ 災害
                                                     ; ⑦ si += 0x20
```

⭐ **`+0x18` 是快取不是狀態**（[`../re/44`](../re/44-threat-and-reinforcement-ai.md) §1）：
每 tick 被佔用圖覆寫一次。它在 ④ 之前更新，所以**威脅判斷讀的是這一拍的值**；
而內政 ⑤ 在 ④ 之後，讀的也是同一拍的值。順序一換，兩者讀到的就是不同拍的快取。

## 3. 為什麼這件事狀態表對拍抓不到

兩個子系統各差一拍，而每一拍的欄位值都會在下一拍被覆寫。
同一個遊戲時刻取樣，兩邊的據點表看起來一樣——差異只在
「**誰在哪一拍做了什麼**」，要逐子刻比亂數消費才看得到
（[`160`](160-rng-consumption-alignment.md)）。

## 4. 驗證

1. 逐子刻對拍（`tools/rng_pace.go -seq-out` vs 原版 `-watch 1ECE0`）：
   5,236 個子刻的不一致數要從 **910／677** 明顯下降，而且

   現在需要兩個不同的值才各自對齊，那正是這條規格要消掉的症狀。

## 4.4 ⚠ 量到的結果：改善，但殘差的主因不在這裡

| | 逐子刻不一致（5,236 拍）| `sub_14057` 觸發次數（原版 191）|
|---|---:|---:|
| 重排前 | 910 | 198 |
| **重排後** | **863** | 199 |

⭐ **真正的殘差來自起始局面不同**：dosgolem 載入存檔後的 `wait` 讓時鐘從
10 時走到 13 時，那 3 小時裡原版跑了 3 次「每小時世界更新」（`sub_13E11`），
而 remake 是從 10 時直接開始。**兩邊的第 1 拍不是同一個局面**，
所以逐子刻比對本來就會有系統性殘差。

⇒ 要把殘差壓下去，要改的是**取樣設計**（讓兩邊從同一個局面起跑），
不是再找規則差異。這一項記在 [`161`](161-liubei-idle-longrun-parity.md) §8。
