# 182 — 月結跑在每「時」更新之前

**狀態：CONFORMED。** 原版的時鐘常式是一層層 fall through：
`loc_11DC1` 的 `call sub_15358`（月結）落在 `loc_11DE0` 的
`call sub_13E11`（每「時」的世界更新）**之前**。remake 的順序相反。

- 日期：2026-09-10
- 出處：`KI.EXE`（松崗 DOS/V，`workplace/ida/dosv/KI.EXE.i64`，
  SHA-256 `6deb8e9c…e5dd62`）`sub_11D8E` 的 `loc_11DC1`／`loc_11DD7`／
  `loc_11DE0`（[`../re/06`](../re/06-game-clock.md) §1）
- 推論等級：confirmed
- 實測：[`../playtest/119`](../playtest/119-rng-pace-comparison.md) §41.5
- 相關：[`../re/07`](../re/07-monthly-settlement.md)（`sub_15358`）、
  [`../re/08`](../re/08-hourly-update.md)（`sub_13E11`）

## 1. 原版做什麼

```asm
loc_11DC1:
        inc  byte ptr ds:0CF4h        ; 月++
        …查每月天數表、日 = 0…
        call sub_15358                ; ★ 月結
loc_11DD7:
        inc  byte ptr ds:0CF0h        ; 日++
        mov  byte ptr ds:0CF3h, 0     ; 時 = 0
loc_11DE0:
        inc  byte ptr ds:0CF3h        ; 時++
        mov  byte ptr ds:0CF2h, 0     ; 子刻 = 0
        call sub_19377                ; 季節漸變
        call sub_13E11                ; ★ 每「時」的世界更新
```

換月會 fall through 到換日、再到換時，所以**同一個小時裡月結先跑**。

## 2. 順序反過來的後果

不是「差一拍」：`sub_13E11` 的第二件事是**預備兵維持費累加**
（勢力記錄 `+0x1A`，[`../re/08`](../re/08-hourly-update.md) §2），
而月結的第四步是**把它歸零**。

順序反過來的話，月初那一小時輪到的勢力會先累加一次、再被歸零——
那一次累加**憑空消失**，而且資金在月結的第一步多扣了同一筆。

同局面 196 年 5 月 1 日 15 時的勢力 7：原版 `+0x1A` ＝ 46、remake ＝ 0，
資金跟著差 46。

## 3. 改了哪一支

`internal/state/state.go` 的 `TickMap`：`ev.Clock.Month` 為真時先跑月結，
月結的最後才呼叫 `hourly`。換月一定也換時，所以那裡不必再問一次
`ev.Clock.Hour`。

## 4. 驗證

`tools/parity_ck.sh` 的拍 3,100（5/1 15 時）與 3,250（5/2 9 時）：
**據點、勢力、軍團、全域四張表全部 0 個 byte**。

## 5. 派發開出玩家視窗時不要提早返回

同一支的第二個順序問題。`sub_13E11` 的第一個呼叫是 `sub_131AE`
（事件派發），而原版的玩家視窗是 **modal**：開完視窗、玩家回應之後，
`sub_13E11` 的其餘三步（侵攻財政檢查、預備兵維持費、外交官）
**照樣跑完**，每時勢力游標因此照樣推進一格。

remake 的 `hourly` 原本在 `w.diplomacy != nil || w.funding != nil` 時
提早返回——而世界暫停已經由 `tick` 開頭那道閘負責了
（`w.pending`／`w.diplomacy`／`w.funding` 任一非 nil 就整個不前進）。
再擋一次的後果是**那一小時的游標憑空少推一格**。

同局面拍 3,291 的外交三選一就是這樣差出來的：拍 3,400（5/3 2 時）
原版游標 11、remake 10。接上之後那一拍的四張表全部 0。

## 6. 未解

- 拍 3,420 的據點 129 上昇值與防災值各差 1——那是拍 3,415 的調兵分歧
  之後的下游（亂數流岔開）。根因已經量出來：據點 `+0x18` 在原版是
  **佔用圖抄來的**（增量維護），remake 是掃座標重算，兩者在
  「在那一格編成、從沒走進來過」的軍團上分岔
  （worklist `tick3415-relief-dispatch-occupancy`）。

## 7. 2026-11-16 財政邊界勘誤

**狀態：CONFORMED，僅此新增財政切片。** 前述月結順序的 CONFORMED 範圍不變。

- 輸入：松崗 DOS/V `KI.EXE`，SHA-256
  `fffeba985231cda4d636e93d10f598470b1f691d00275e4aa38e285893d43868`。
- 工具及位址：IDA Pro 9.4 database linear，基準 `0x10000`；既有匯出
  `workplace/matching-decompilation/c-hourly/ida/ida-probe.json`。
- 原始指令：`0x13E33 3b4421` 比較 `AX` 與 `[si+21h]`，
  `0x13E36 7c0e` 為有號 `jl`；未跳過便在 `0x13E38 c64419ff` 清除目標。
  第二次比較在 `0x13E3E 3b4421`，`0x13E41 7c03`，未跳過便設 bit 6。
- 已證實：令 `H = signed16([勢力+0x21])`，`T = 據點數×8+24`，
  原版取消侵攻條件是 `H <= T`，資金吃緊條件是 `H <= T/2`。
  舊文件與 Go 將第一條寫成 `<`，把第二條改成先把資金加倍，都不等價。
- 可見案例：固定種子原版續跑至 196/6/14 5時子刻8，勢力11有19個據點，
  資金45,182，`H=T=176`；原版目標為 `0xFF`，remake 仍為14。
  兩側此時佔用圖98,304 bytes及亂數258 bytes相同。後者因此多取一次求援亂數。
- 垂直鏈：存檔有號24位資金 → `Faction.Funds` → 每時財政檢查 →
  AI軍團與據點威脅判斷 → 原有地圖呈現 → `World.Bytes` 保存目標與bit 6。
  不新增玩家設定或改存檔格式。
- 驗收：原始指令及已載入 bytes 相符；原版財政切片遍歷據點數0…192，
  兩道門檻前後及低位元組邊界；Go規則與每時路徑測試；同一4/16存檔與種子
  重跑至7/16六張表。切片對拍不取代正常玩家路徑。
- 收據入口：`workplace/scratch/ai-rng-20261116/`。既有完整原版續跑、逐次亂數、
  每日六表及焦點上下文均保留；未驗完前不宣稱長局通過。
- 證據審查：原版 `0x13E22` 至 `0x13E46` 財政切片19,300組全部符合上述
  兩道比較，包含資金低byte為0、1、127、128、255及初始bit 6兩種值。
  已驗證 `sub_13E11` 的IDA匯出bytes、EXE檔案bytes、執行器載入bytes三者相同。
  原版收據 `finance-original.jsonl`、`finance-original-proof.json`；只屬局部入口驗證。
  正式規則可依此修正，長局及正常路徑驗證尚待完成。
- 實作後的每時存讀檔測試另發現：`LowFunds` 雖有 typed 欄位，載入與寫回皆漏接
  勢力 `+0x00` bit 6。依原版 `0x13E22` 先清、`0x13E43` 再設的既有證據，
  READY契約補明：載入解出此bit，寫回只更新此bit並保留其他旗標；不得重算或遺失。
  測試首輪失敗收據保留，補齊後重新跑同一每時／存讀檔測試與六表驗收。
