# 05 — 一張靜止的截圖就把據點座標定案了

**狀態：`SINARIO.DAT` 的據點 X／Y 座標升到 confirmed。**
`docs/formats/08` §4 原本寫「要定案得在遊戲裡看」——結果不必進遊戲，
**手上早就有那張畫面了**。

- 日期：2026-08-08
- 材料：`workplace/dosbox/shots/r3.png`（PC-98 實機，640×400）
  ＋ `workplace/shots/mmap.raw`（解好的 384×256 地圖格）
  ＋ `workplace/orig/pc98/SINARIO.DAT`

## 1. 那張截圖不是開場動畫

先前四輪自動化都記成「開場還在播，鍵盤跳不過」。實際上是
**戰略地圖 ＋ `NEW GAME` YES／NO 對話框**，遊戲早就開完機了。

發現的方式是免錢的：跨三小時、四次獨立執行的截圖 **md5 完全相同**。

| 檔案 | 時間 | md5 |
|---|---|---|
| `w01`／`y01`／`z01`／`z04` | 03:43–03:56 | `98ed3eed…` |
| `r1`／`r2`／`r3` | 11:01–11:03 | `98ed3eed…` |

會動的東西不會 pixel 相同。**四次一模一樣本身就證明它是靜止畫面**，
而靜止畫面在這個遊戲裡只有一種可能：在等輸入。

> 教訓與 `docs/playtest/04` §0 同源：**先問「我看到的到底是什麼」，
> 再問「為什麼我的輸入沒用」。** 那一輪問對了輸入，這一輪才問對了畫面。

## 2. 用「水的形狀」把畫面對回地圖

PC-98 的調色盤與這邊的解碼不同，比顏色沒有意義。比的是**水在哪裡**：
河與海分佈稀疏、圖樣獨特，而且藍色不會認錯。

```
地圖側：mmap.raw 的圖塊編號 → 查「這個編號畫出來是不是藍的」→ 384×256 布林
截圖側：640×376 的地圖區切 16×16 → 每塊算藍色像素比例 → 40×23 布林
```

把 40×23 的窗在 384×256 上滑一遍（80,730 個位置，每列壓成整數用位元運算比）：

| 狀態列高度 | 可用格 | 最佳位置 | 一致率 |
|---|---|---|---|
| 24 | 738 | (170, 97) | 97.7% |
| **32** | **725** | **(170, 98)** | **100.0%** |
| 16 | 702 | (170, 97) | 99.3% |
| 8 | 709 | (170, 97) | 96.8% |
| 0 | 673 | (170, 96) | 98.1% |

五個高度的最佳 `ox` 全是 170，`oy` 隨高度每 16 px 移一格
（32→98、16→97、0→96）——彼此自洽。

### ⚠ 一致率高不代表對，先看基準線

上一輪選錯 `BATTLE.SCH` 解碼就是栽在「可以被灌水的指標」
（`docs/formats/07` §8）。所以先把基準線量出來：

```
全部猜「不是水」        →  666/725 = 91.9%
一致率 ≥ 90% 的位置     →  19,273 個
一致率 ≥ 95% 的位置     →  3 個
一致率 = 100% 的位置    →  1 個
```

**91.9% 是白送的**，所以「95% 很高」是錯覺。真正的訊號是：
725 格裡有 59 格是水，而 (170, 98) 把 59 格水**和** 666 格陸地
同時全部擺對，是八萬個候選中唯一超過 95.1% 的。

於是拿到三件事實：

- 上方狀態列高 **32 px**
- 大地圖以 **16 px／格、對齊格線**繪製（不是任意像素捲動）
- 這個畫面的左上角是圖塊 **(170, 98)**

## 3. 把據點座標投影上去

視窗確定之後，`SINARIO.DAT` 的座標可以直接算成畫面位置：

```
畫面 x = (記錄 X − 170) × 16
畫面 y = 32 + (記錄 Y − 98) × 16
```

視窗內有 8 個據點（四個劇本的座標完全相同，據點位置不隨劇本變）。
量每一格「非草、非水、非黑」的像素比例——城池的磚牆與屋頂會落在這一類：

| 據點圖塊座標 | 投影到畫面 | 比例 | 在全畫面 824 格中的分位 |
|---|---|---|---|
| (173, 101) | (48, 80) | 86.7% | 前 2.7% |
| (202, 101) | (512, 80) | 92.2% | 前 1.1% |
| (192, 102) | (352, 96) | 86.7% | 前 2.7% |
| (200, 106) | (480, 160) | 92.2% | 前 1.1% |
| (171, 112) | (16, 256) | 86.7% | 前 2.7% |
| (206, 114) | (576, 288) | 86.7% | 前 2.7% |
| (191, 119) | (336, 368) | 86.7% | 前 2.7% |

全畫面的中位數是 33.2%。七個點同時落進前 2.7%，機率約 10⁻¹¹。

**第 8 個 (187, 107) → 畫面 (272, 176) 正好在對話框底下量不到**
——這一點本身也對得上。

### 錨點偏移是 0

掃 `dx, dy ∈ [−2, 2]` 找最佳錨點，**最好的就是 (0, 0)**：
記錄裡的座標**直接是**城池圖案所在的那一格，不需要任何修正。

`docs/formats/08` §4 原本寫「最佳偏移 `dx=+2` 也只有 41.7%」——
那是拿圖塊編號在地圖格上掃「像不像城池圖塊」得到的，判準本身很鬆。
**實機畫面把它蓋掉了。**

## 4. 順帶驗掉的東西

- **`MMAP.MAP` 的 RLE 解碼與 `MMAP.MDL` 的圖塊編號都是對的。**
  725 格水陸分佈 100% 吻合，錯一個 byte 都不會這麼齊。
- **`MMAP.MAP`／`.MCH`／`.MDL` 在 PC-98 與 DOS/V 兩版 byte-for-byte 相同**
  （md5 三個檔都一致）。所以 PC-98 的畫面可以直接當 DOS/V 分析的 oracle，
  不必擔心兩版地圖不同。

## 5. ⭐ 方法論：oracle 卡住時，先清點「手上已經有的觀測」

`docs/playtest/04` §6 列了四件「卡在滑鼠自動化後面」的事。回頭看：

| 當時記的 | 現在 |
|---|---|
| 據點座標驗到 confirmed | **本文做完了**，用的是早就存在的截圖 |
| `docs/mechanics/15-realtime.md` | 早就 READY——答案在說明書與機器碼裡，根本不需要 oracle |
| 地形類型命名 | 已用鄰接統計推翻 5 號的判讀（`CONTEXT.md` §6） |
| 戰場圖塊像素格式 | 已解（`docs/formats/07` §8–§10），用的是檔案自身的遮罩不變量 |

**四件都不需要那個被卡住的能力。** 那份清單在寫下的當下就已經過時了。

把「受阻」寫進文件會讓它看起來像一道閘，於是每一輪都繞著閘打轉。
真正該做的是：**在動手解閘之前，先把閘後面那張清單逐項重問一次
「這件事真的需要它嗎」。** 這一輪四項全是「不需要」。
