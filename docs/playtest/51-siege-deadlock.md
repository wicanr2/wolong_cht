# 51 — 攻城戰打不完：同狀態對拍挖出來的死鎖

**狀態：修好了，兩件。** 那條攻城 fixture 在修正前跑到 12,000 幀還是
`Done=false`，而且從第 1,600 幀起**一個 byte 都沒變**；同一輪還量到
守方從頭到尾一兵未損。兩個成因各自獨立：**退卻的兵鎖死在半路**
（[`../spec/94`](../spec/94-retreat-path-not-cleared-every-frame.md)）、
**開場擺兵的高度用錯了表**（[`../spec/95`](../spec/95-spawn-height-uses-ground-plane.md)）。
修完之後第 **1,192 幀**結束，兩軍真的打起來。

- 日期：2026-08-27
- 規格：[`../spec/94`](../spec/94-retreat-path-not-cleared-every-frame.md)、
  [`../spec/91`](../spec/91-tactical-parity.md) §3（同狀態怎麼湊）
- fixture：`workplace/promo-live/parity-battle4/SAVE-E.DAT`（196年5月10日）、
  據點 82、軍團 **81 張遼攻／39 夏侯惇守**、玩家守方、seed 7
- 量法：規則層直接跑（`Battle.Step`），不經畫面

## 1. 起點：把對拍的 fixture 換成同一場

[`49`](49-parity-retest-20260827.md) 的攻城那一組用 `-open-siege` 從**開局劇本**
現編軍團，開出來的是袁術軍——而原版擷取的是張遼軍攻許昌。
側欄那幾區的差異幾乎全是人名。

改成拿存檔裡現成的兩支軍團開戰（`-siege-corps 81,39`），差異立刻塌下來：

| 區 | 現編軍團 | 同一批軍團 |
|---|---:|---:|
| `sb-title` | 2.16% | **0** |
| `sb-self` | 4.52% | **0** |
| `bottom` | 1.71% | **2 px** |
| `sb-enemy` | 3.22% | **14 px** |
| `field` | 0.86% | 0.84% |
| `sb-minimap` | 1.48% | 1.64% |

⭐ **側欄那四區本來就是對的。** 差異全部來自「兩邊開的不是同一場」。

## 2. 原版那一張畫面同時給了三個讀數

同狀態之後就能拿畫面反推原版當時的內部值：

| 讀數 | 換算 | 原版的值 |
|---|---|---|
| 門強度條 93 px | `min(耐久 >> 4, 151)` | 城壁耐久 **1,488–1,503** |
| 對方體力條 120 px | `min(值 × 3 ÷ 4, 124)` | 大將體力 **160–161** |
| 對方兵力條 121 px | `min(值 >> 2, 124)` | 兵力 **484–487** |

拿 remake 的曲線去對，**三個讀數指向三個不同的幀**：

| 讀數 | remake 對應的幀 |
|---|---:|
| 城壁耐久 1,495 | 約 225（160 幀時 1,632、250 幀時 1,441）|
| 大將體力 160 | 400 |
| 兵力 485 | 從沒發生——遠在 1,200 之後 |

⭐ **沒有任何一個 remake 的幀能同時對上三個。** 這不是取樣點沒對準，
是**速率不一樣**：remake 的攻方整團擠在城壁前猛打（城壁掉得快），
而原版那一刻攻方已經折損了約 115 點兵力。

## 3. 順著兵力那條線往下：守方一兵未損

規則層直接量（`SAVE-E.DAT`、據點 82、seed 7）：

| frame | 側 0（張遼／攻方）| 側 1（夏侯惇／守方）|
|---:|---|---|
| 0 | 活 48、兵 600、體力 200 | 活 48、兵 600、體力 200 |
| 400 | 活 48、兵 600、體力 160 | **完全不變** |
| 1,200 | 活 48、兵 600、體力 80 | **完全不變** |
| 1,600 | 活 23、兵 197、體力 40 → 全軍退卻 | **完全不變** |
| 4,000 | 與 1,600 逐欄相同 | **完全不變** |

守方 48 人全活、兵 600 一點沒掉。成因量得出來：
**守方站在 Z=1，攻方在 Z=0**，而 `doAttack` 的碰撞要求 `s.Z == e.Z`——
攻方走到守方腳下就停在那裡，目標寫著 `(5,32,1)`，永遠上不去。

再往下一層，那個 Z=1 是**擺兵時用錯了表**：`Place()` 讀圖塊堆疊高度
（`StandLevel`），而移動時 `tryMove` 把 Z 同步成地面層（`GroundLevel`）。
兩個表在這張圖上**沒有一格相同**：

```
側1 兵 0 (3,32)  堆疊 1　地面層 0
側0 兵 2 (60,34) 堆疊 2　地面層 0
96 個兵裡有 96 個的兩個值不一樣
```

所以「沒動過的兵」停在移動層之上，而**走過來的兵掉到移動層**——
同一格差一層。改用 `standZ`（`doFormation` 早就在用的那一支）之後
兩軍終於交手（[`../spec/95`](../spec/95-spawn-height-uses-ground-plane.md)）。

⭐ **這是內部矛盾，不是「哪一個表才對」。** 站著不動的兵與走過來的兵
落在同一格卻不同層，這個狀態在任何一種解讀下都不成立——
**不必先讀出原版寫哪一個，就知道現況是錯的**。

## 4. 死鎖：兩處各自都足以卡住

攻方大將的體力被攻城計時器（`sub_1AE56`，每 10 幀 −1）耗到 50 以下，
全軍轉退卻。然後就再也不動了。

**第一處**：`doRetreat` 每一幀把 `s.Path` 設回 nil。一幀之內是
`doRetreat` → `moveToward`（用路）→ 走不動 → `replan`（算路），
清除在最前面，所以算好的繞路點**下一幀開頭就被丟掉**。
配上「退卻中的同伴不能對調」（`sub_1B732` 的閘），一整排鎖死。

逐幀追大將：位 (22,32)、目標 (62,32)、**步 (62,32)**，而繞路點是 (22,31)。
量過 (22,31)：地面層 0、上方沒東西、**沒有人站著**——它走得過去，
只是從來沒有被叫去走。

**第二處**：改掉之後兵前進到 X 43 **又卡住**。`replan` 開頭的
`if s.Path.Len() > 0` 讓它抱著一條穿過同伴的直線路永遠不重算。

兩處都改掉之後：第 1,416 幀結束，攻方 48 人全部退出畫面，守方勝。

## 5. 教訓

> **一、有一支「戰鬥會結束」的測試，而它照樣是綠的。**
> `TestNormalScenarioTacticalBattleTerminates` 跑的是**玩家攻城**——
> 戰場不翻、玩家那一側是攻方，那一場在任何人退卻之前就分出勝負了。
> 死鎖只在**玩家守城**那一邊。**同一種形狀的測試要涵蓋兩種擺法**，
> 而「攻守互換」正是這一款把戰場轉 180 度的那個開關（`spec/56`）。

> **二、對拍的價值不只在像素。** 這一輪真正的收穫不是 0.84%，
> 是「三個讀數指向三個不同的幀」——**同一張畫面上的每一個計量條
> 都是一個獨立的讀數**，兜不攏就代表模型不對，而不是取樣點沒對準。

> **三、`Done` 為 false 不是狀態，是問題。** 一場永遠不結束的戰鬥在
> 遊戲裡是掛住；而在測試裡它長得像「還在跑」。**跑不完要當紅燈看**。
