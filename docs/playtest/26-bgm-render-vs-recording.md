# 26 — 合成出來的音樂對得上原版錄音

**狀態：confirmed。`internal/audio` 渲染的 `OPENBGM.DAT` 與 DOSBox 錄的同一首，
包絡互相關 0.704（單一尖峰，中位數 −0.045），頻譜前十個峰值有七個相同。
⭐ 這個比對也是「音高表被讀成 32 筆」那個錯**唯一**被抓到的地方（§3）。**

- 日期：2026-08-15
- 渲染側：`tools/go.sh run ./cmd/wlbgm -bgm workplace/orig/dosv/OPENBGM.DAT`
- 錄音側：`workplace/dosbox/audio/d7open  _000.wav`
  （14.9 秒，DOSBox 0.74，來源見 [`25`](25-audio-capture-feasibility.md)）
- 比對腳本：一次性，未進版控（方法寫在 §2，重跑得起來）

## 1. 為什麼需要這個比對

解格式那條路上的每一層都能「自洽地錯」：

| 層 | 錯了會怎樣 |
|---|---|
| 事件編碼 | 解出來的音名／時值仍落在合法範圍 |
| 音高表 | 整首曲子平移幾個八度，**聽起來仍然是同一首** |
| 速度換算 | 整首等比例變快變慢，音符關係不變 |
| 音色 | 音對但音色不對 |

前三項**用原版資料自己驗不出來**——它們的內部一致性檢查全都會通過。
要抓出來只能拿一個外部參照，而 [`25`](25-audio-capture-feasibility.md)
錄的那 14.9 秒正好是。

## 2. 兩個比對

### 2.1 頻譜峰值（驗音高）

兩邊各取同一段做 8192 點 FFT，列平均頻譜的前十個峰值：

| 渲染 | 錄音 |
|---|---|
| C6 1033.6、A5 877.5、E7 2621.7、G5 780.6、D6 1168.2、A7 3504.5、F7、G7、D7 2293.3、C8 | A5 877.5、C6 1033.6、A7 3606.8、E7 2621.7、F8、C#7、A7 3504.5、G5 780.6、D7 2293.3、G7 3063.1 |

**七個峰值落在同一個頻率格**（877.5、1033.6、2621.7、3504.5、780.6、2293.3、G7 附近）。

### 2.2 包絡互相關（驗速度）

把兩邊降到 100 Hz 的 RMS 包絡，用錄音那 14.9 秒在渲染的 60 秒上滑動：

```
最佳對齊  相關 0.704  於 0.71 秒
次佳      相關 0.704  於 0.72 秒（同一個尖峰）
中位數    相關 −0.045
```

**單一尖峰**，而且落在 0.71 秒——也就是錄音幾乎是從曲子開頭開始的。
tick 速率若算錯，包絡會被等比例拉伸，14.9 秒的節奏圖樣不可能在任何位移上對上。

## 3. ⭐ 這個比對抓到的東西

第一次跑的時候，渲染的頻譜峰值全部落在 21–290 Hz，錄音在 780–5690 Hz
——**整整差四個八度**。原因是音高表 `0AD0` 被讀成 32 筆，
實際是 128 筆（`docs/re/56` §3.2）。

⚠ **當時已經有的三個檢查全部照樣通過**：音色編號落在表內、
十二平均律的比值、音域分層。它們都只碰得到表的前 1/4。

**能通過的檢查沒有覆蓋到的地方，錯誤就住在那裡。**
這也是為什麼 `internal/audio` 的音高測試要跨八度驗，不是只驗一個八度。

## 4. 順帶解掉的一個疑問

[`25`](25-audio-capture-feasibility.md) §4 把「錄到的峰值只有滿刻度 4.7%」
列為未解。渲染結果顯示**曲子前段本來就是輕的**（音量 7，
比主段的 12–14 低約 21 dB），而那 14.9 秒正好整段落在前段。
不是錄音鏈路的問題。

## 5. 未解

| 項目 | 現況 |
|---|---|
| 音色的聽感 | 頻譜只驗了基頻。諧波結構（也就是「像不像那個音色」）沒有量化比對 |
| 相關係數為什麼不是 0.9 | DOSBox 的 OPL 模擬與這顆的包絡實作不同，加上錄音有系統噪訊。**沒有排除「還有小錯」的可能** |
| 其他曲子 | 只有開場曲有錄音對照組。另外 13 首沒有 |
