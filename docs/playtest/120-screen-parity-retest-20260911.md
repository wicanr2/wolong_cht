**狀態：不通過。** 規則層的同狀態對拍已經到 196 年 5 月 31 日
（拍 9,177、66 個取樣點、六張表逐 byte 相同），但**畫面那一側落後了**：
主畫面五區裡一區 NEAR、野戰九區裡一區 NEAR 一區 FAIL，攻城那一組
**重跑不出來**（原版取樣圖對不上號）。

三組都用「這一輪之前的程式碼」（`c2c3522`）重截驗證過——
**數字一模一樣**，所以不是 2026-09-11 這一輪的規則改動造成的。

- 日期：2026-09-11
- 為什麼跑：使用者要打包發行，條件是「規則與畫面都跟原版對拍」。
  這一輪動過 `internal/battlesetup`（戰場取樣的位移，
  [`../spec/196`](../spec/196-field-battle-rolls-the-battlefield.md)），
  畫面那一側必須重驗
- 原版側：沿用既有受控擷取，`tools/parity_crop.py` 切成 640×400
- remake 側：`tools/parity_shot.sh` 用現在的原始碼重截
- 比對：`tools/py.sh tools/parity_diff.py`

### 1.1 主畫面那 101 px 是同一個圖塊的相位差

差異落在 x 320–335、y 208–223 —— **正好一個 16×16 的格子**，在地圖正中央。
把兩邊那一格印成點陣圖，是**同一種格子紋樣**，只是 remake 的往下錯開
一到兩列：

```
原版    remake
######################  ##############.#
#+#+++###+#+++##        ##...........##.
#+#+++###+#+++##        #..+++###+#++.#.
```

⇒ 不是畫錯圖塊，是**取樣的相位**（或那一格的動畫階段）差一點。

## 2. 都不是這一輪造成的

`git checkout c2c3522 -- internal cmd` 重截，再比同一張原版圖：

| 組 | 這一輪的程式碼 | `c2c3522`（這一輪之前）|
|---|---|---|
| 主畫面 `map` | 101 px | **101 px** |
| 野戰 `field` | 190 px | **190 px** |
| 野戰 `sb-minimap` | 128 px | **128 px** |

⇒ 落差是 2026-09-02 之後某一輪引入的。那段期間的每一輪都在改規則層
（行軍、戰鬥、AI、月結），**沒有一輪回頭重跑畫面對拍**。

⭐ 這正是 `CLAUDE.md` §10 那條「測試綠不等於原版 parity」的另一面：
**規則對拍綠了，不代表畫面對拍還綠**——兩者是兩套證據，而規則層的
每一次改動都可能動到畫面。

## 3. 攻城那一組重跑不出來

[`58`](58-parity-retest-20260902.md) §1.2 的三個取樣點寫的是
`-battle-steps 160/240/300`，原版側只寫「`workplace/promo-live/parity-battle4/`」
——**沒說哪一張 PNG 對應哪一拍**，而那個目錄裡只有一張 `h4-ordered.png`。
拿 [`40`](40-tactical-parity.md) 的 `probe-march/e10.png` 去比是 12.05%，
那是取樣點不等價，不是回歸。

⇒ **對拍紀錄要寫得能重跑**：原版圖的路徑、取樣點、命令三者要同時在場。
這一條已經是 `tools/stale_scan.py` 在擋的那一類（對拍紀錄的 `remake 側`
漏了受控存檔），只是它擋不到「原版側漏了是哪一張圖」。

## 4. 未解

- 主畫面 `map` 那 101 px 的相位差是誰造成的（2026-09-02 之後的某一輪）。
- 野戰 `field` 95 → 190、`sb-minimap` 32 → 128 的成因。
- 攻城的取樣點與原版圖要重新對上號，或重跑一次受控擷取。
