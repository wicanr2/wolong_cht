# 89 — 進言三條 `map` 0 px；遷都那張露出「內政吃亂數」

**狀態：通過（進言三條）／已歸因（遷都）。** 用受控存檔
（[`88`](88-controlled-save-parity.md)）把雲關掉之後，進言的敵對／停戰／
請求協助三張**`map` 全 0 px**。遷都那張剩 805 px，逐欄看下來是
**據點的上昇率差到 ±4**——把取樣點對到子刻也沒改變，
所以那不是取樣granularity，是**內政本身吃亂數**、兩邊各自擲骰。

- 日期：2026-09-06
- 規格：[`../spec/140`](../spec/140-status-message-box.md) §1.1（狀態列）、
  [`../spec/126`](../spec/126-command-popup-menus.md) §1.2（選完不擦）、
  [`../spec/147`](../spec/147-controlled-parity-save.md)（受控存檔 ＋ 亂數狀態）
- 原版側：`WOLONG_DOSGOLEM_GAMEDIR=dosgolem/root-noclouds tools/dosgolem.sh …
  "…;sclick:352,15;stap:48,47;steps:400000;<move:48,200 × N>;press;steps:900000;shot:…"`

## 2. 抓到兩件事

**一、進言選單選走之後原版也不擦。** 與指令列那三張彈出選單同一條規則
（[`../spec/126`](../spec/126-command-popup-menus.md) §1.2）：目標一覽表直接畫在它上面，
露出來的那一列一直掛在清單上緣。remake 先前選完就把框收掉，
所以少了那一列。接法也一樣——`adviseMenuStale`，地圖一重畫就清。

**二、`-advise-target` 沒走真實路徑。** 它只 `openAdvise` ＋ `pickAdviseCommand`，
沒開命令視窗、沒設反白格。補上之後 `command` 從 98.69% 掉到只剩游標。

⭐ 順帶修掉一句過期註解：`openCapitalList` 寫著「原版是 `sub_17400` 的
**地圖選點**」——**不是**，`sub_17400` 是據點一覽的呼叫端
（[`../re/26`](../re/26-list-window-engine.md) §4.1），原版擷取也證實遷都開的是一覽表。
兩邊操作方式相同。

## 3. 遷都那 805 px：不是取樣，是亂數

逐欄比（原版 → remake）：

```
上昇率  8→9  8→9  6→6  3→0  7→6  8→12  14→12  6→9  9→11  5→6
防災   107→107 109→110 105→105 109→110 112→111 …    （全部 ±1）
城兵   1300→1300 1360→1350 1610→1620 980→1000 …     （±1 單位）
```

防災與城兵落在 [`83`](83-city-list-parity.md) 已裁定的 ±1 內，
**上昇率不是**——差到 4。

⭐ 先排除取樣：`-shot-when` 這一輪加上了**子刻**（`clock:年/月/日/時/子刻`），
原版那一刻的子刻用 `ipeek:10CF2:1` 讀（時鐘在 `cs:0CF0h`，`+0x02` ＝ 子刻）。
對到同一個子刻之後**數字一個都沒變，805 px 也沒變**——所以不是取樣點。

成因是**內政本身吃亂數**：`sub_14194` 每次整備取一個 byte
（remake 是 `governor.Tick` 的 `rng.Next()`）。兩邊的亂數流不是同一條，
跑一個遊戲日就差開。**這一項不是規則分歧。**

## 4. 亂數狀態可以搬過來

原版的產生器狀態只有 258 byte 而且都在固定位址
（[`../spec/147`](../spec/147-controlled-parity-save.md) §5）。
`runto:11CD0`（主迴圈第一拍）停住之後讀：

```
時鐘 10 1E 03 0A 04 00 C4 00   ＝ 196/4/16 10 時 子刻 3 ← **與存檔一模一樣**
亂數 1ECFC = 00 00 E9 A8 …     ＝ c = 0、s = 0，只有置換表是播種來的
```

⭐ **`c` 與 `s` 都還是 0**——載入之後、第一拍之前，遊戲一個亂數都沒抽過。
所以那一刻的狀態就是「乾淨的起點」，把 258 byte 灌進 remake
（`-rng-state`）兩邊就從同一個起點跑同一條流。

### ⚠ 量完了：搬過去**沒有變好，反而更差**

同一張原版擷取（`orig-a15c`，196/4/17 6 時），remake 兩種跑法：

| remake | `map` 不同像素 |
|---|---:|
| `-seed 7`（自己的亂數）| **286** |
| `-rng-state`（灌入原版的表）| 421 |

**灌了反而更差。** 這不是機制壞掉——`TestFromRawReproducesTheSameStream`
證明兩邊會吐出同一串數。壞的是**消費順序**：兩邊在同一拍取的亂數個數不同，
序列從第一個不一致的地方就岔開，之後只是**換一種岔法**，不是變接近。
`-seed 7` 那一次比較接近純屬運氣。

⭐ **所以這個機制目前的用途不是「讓對拍變準」，是「把岔開的位置變成看得到的東西」**。
真正要做的下一步是**逐拍數兩邊各取幾個亂數**，找出第一個不一致的地方。

⭐ 另一個更實用的結論：**經過時間才是主因**。同一條流程

| 取樣點 | 距離載入 | `map` |
|---|---|---:|
| 196/4/20 20 時 | 約 4 個遊戲日 | 805 |
| 196/4/17 6 時 | 約 20 個遊戲小時 | **286** |

**含動態欄位的畫面要在載入之後盡快取樣**——把 `until:` 拿掉就少一半誤差。
