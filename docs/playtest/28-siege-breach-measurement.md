# 28 — 量攻城：remake 的攻方打不進城，原因是城牆四格厚

**狀態：⚠ 缺口已定位，三個 parity bug 已修並有單測；
**攻方仍然攻不進城**。原版靠爬上牆頂，而**機制已經在同一天解完**
（[`../re/63`](../re/63-ground-plane-map.md)）：登城點是圖塊 ≥ `0xF0` 的門格。
這一份記的是量測與當時的追查過程，**實作還沒做**。

- 日期：2026-08-16
- 素材：`workplace/orig/dosv/BATTLE.MAP`／`BATTLE.MDL`／`BATTLE.DAT`、
  `KI.EXE` 的陣形表（`LoadFormations`）
- 方法：無頭跑 `internal/rules/tactical`，用真實戰場、真實高度表、
  真實陣形表，固定亂數種子

## 1. 量到什麼

三張攻城圖（0、5、20），雙方各六隊步兵滿編，攻方下突擊／攻擊／城壁移動：

| 圖 | gateX | 城壁耐久 | 撞擊次數 | 結束幀 | 攻方場上 |
|--:|--:|--:|--:|--:|--:|
| 0 | 36 | 1,820 | **0** | 550 | 0 |
| 5 | 42 | 5,300 | **0** | 560 | 0 |
| 20 | 35 | 1,660 | **0** | 550 | 0 |

**三種命令的結果完全一樣。** 攻方在 50 幀內從陣形線走到城牆前，
之後 X 分佈到第 450 幀**一格都沒有變**，一次也沒碰到城壁，
最後在第 550 幀左右全軍退場。

那個 550 不是巧合：**攻城方大將每 10 幀掉 1 體力，掉到 50 觸發全軍退卻**
（[`../re/11`](../re/11-tactical-battle.md) §5.8h）。也就是說
**攻方是被內建的攻城計時器耗死的，不是被守軍打死的**。

## 2. 為什麼撞不到：當時的地形模型把整面牆算成實心

圖 20、y=32 那一列的圖塊是 `02 02 10 DD 10 10 04`。
當時的 remake 用「堆疊高度以下全實心」算通行，於是 `10`／`DD` 那四格
（堆疊 5）全部變成擋路，兵連可破壞的 `DD` 都碰不到。

⭐ **那個模型是錯的。** 原版的判準是**子圖塊 ≥ 0x70 不擋人**
（`sub_1BB6D`，[`../re/63`](../re/63-ground-plane-map.md) §2）：
`0x10` 的七層是 `98 00 00 2f 7d 00 00`，第 0 層就是可以站的頂面，
**根本不擋**。照原版重算之後，城門那一列**只有一格擋著**，
打壞它整列就通（迴歸測試 `TestBreakingWallOpensCorridor`）。

⇒ 所以攻城有兩條路：**撞開城門那一格**，或**從門那一格登上牆頂**
（[`../re/63`](../re/63-ground-plane-map.md) §4）。
說明書「騎馬のみの編成では城壁に登れない」講的是後者。

## 3. 本輪修掉的三個 parity bug

| bug | 原版怎麼寫 | 出處 |
|---|---|---|
| **突擊會開門**（雙方都會，而且拆的是門）| **只有守方**觸發，而且拆的是**所有完好的城壁**（類型 1）。門不在裡面 | `sub_1B7CB` 的側別閘 ＋ `80 FC 01`（`cmp ah, 1`）|
| 被地形擋住的兵不重算繞路 | — | 對調（`sub_1B732`）回報「走成功了」，於是前排靠跟後排換位一直算有移動。原版的繞路點是在**命令生效那一刻**算的（`sub_1AED2`）|
| 純地形走不通就整個不動 | — | remake 的近似：改成允許「撞穿還沒破的城壁／門」，並照**打壞後的高度**（瓦礫，高度 0）算路 |

第三項是 remake 的取捨，不是原版行為——原版走的是
`0x1800 + 兵編號 × 128` 那張預先算好的繞路點清單，
而那個演算法還沒解出來。

## 4. 修完之後：§1 的數字沒有改變

`TestPathFallsBackThroughBreakableCells` 用一張被單格城壁完全封死的圖驗過：
純地形尋路回空、允許撞穿之後找得到路、打壞之後純地形也通。

真實攻城圖上的數字沒有改變——原因是 §2 的地形模型，
在[`30`](30-ground-planes-implemented.md) 才修掉。
**這一份不宣稱攻城已經可玩。**

## 5. 未解

### 5.1 ⭐ 登城機制：`sub_1B1B1` 已經讀了一半，缺的是那兩張地面高度圖

水平跨格的碰撞判定全在 `sub_1B1B1`（`0001B1B1`，143 B）：

```asm
0001B1B5  al = es:[bx] / test al, 7Fh / jnz .擋      ; ★ 目標格有**單位**就擋
0001B1BC  ah = es:[bx+1000h] / test ah, 7Fh / jnz .擋 ; 上面那一層有單位也擋
0001B1C6  and ah, ah / jnz .沒有地面                   ; 上層是地形 → 失敗
0001B1D2  dx = bx / dh &= 0Fh / dh |= [si+1Eh]        ; ★ PlaneHigh 選 plane
0001B1DC  dl = es:[di+7000h] / and dl, 7               ; ★ 那一格的地面層
0001B1E8  cmp di, 1000h / jnb .高平面
          ; ── 低平面 ──
0001B1EE  cmp dl, [si+0Ah] / ja .升 / jb .降 / clc retn
.升:      bx += 1000h / inc [si+0Ah] / inc [si+12h] / clc / retn
.降:      bx -= 1000h / dec [si+0Ah] / dec [si+12h] / clc / retn
          ; ── 高平面 ──
0001B1F7  cmp dl, [si+0Ah] / jnz .失敗                 ; ★ 高度必須完全相等
0001B207  dl = 圖塊值 / cmp dl, 0F0h / jb .通過
0001B210  cmp dl, 0F8h / jb .失敗                      ; 沒破的門擋
0001B215  cmp byte [si+1Ah], 6 / jz .失敗              ; 命令 6 也擋
```

三件確定的事：

1. **擋路的是「單位」，不是地形高度。** 城壁與門是同一個陣列裡的實體
   （[`../re/11`](../re/11-tactical-battle.md) §5.11），所以它們擋；
   城體那種純地形不在陣列裡。
2. **低平面的水平跨格沒有高度差上限**——目標格地面比自己高就升一層、
   低就降一層，**兩種都算走成功**（`0001B1EE` 那三行，沒有 magnitude 檢查）。
   remake 的 `abs(z − s.Z) > 1 → 擋住` 不是這一條。
3. **高平面要高度完全相等**，而 `[si+1Eh]`（`PlaneHigh`）決定讀哪一張。
   它只由純 Z 移動那一支寫（`sub_1B0D3` 寫 `0x10`、`sub_1B116` 清 0），
   而純 Z 那一支正是 `cmp byte ptr [si+4], 12h / jbe` 擋住大將與騎馬的地方。

⇒ **登城 ＝ 先用純 Z 爬到高平面，再在高平面上水平走。**
這同時解釋了「騎馬爬不上城牆」——**限制在純 Z 那一支，不在水平跨格**。

⚠ **還沒解的是那兩張地面高度圖本身**（`es:[di+0x7000]` 與
`es:[di+0x8000]`，各 4,096 格、低 3 位是地面層）：誰填的、
高平面的值怎麼來的。沒有這一段就不知道「爬到哪一層算上牆」，
所以本輪**沒有實作**——試著照低平面那條規則改，會讓
`TestCavalryCannotClimb` 與 `TestFacingOnlyUpdatesOnSuccessfulMove` 同時翻掉，
而那兩條測試釘的是既有 RE 的結論。**訂正比新結論需要更硬的證據。**

### 5.2 ⭐ 那兩張地面高度圖：在另一個段，已經解出來了

全庫沒有用 `+0x7000` 位移寫它的指令是對的，**因為建置端用的是另一個段變數**
（`word_1D2FC`，正好接在通行圖 `word_1D2FA` 的 `0x7000` 之後）。
建置在 `sub_1BBA6` → `sub_1BC39`，判準是「子圖塊 ≥ `0x70` ＝ 可以站的頂面」，
低平面取層 0–3、高平面取層 4–6，之後整面牆頂被正規化成單一高度。
**上下城牆只在圖塊 ≥ `0xF0`（門）那一格做**——城牆本體爬不上去。

完整推導見 [`../re/63`](../re/63-ground-plane-map.md)。以下留當時的追查過程。

### 5.2.1 當時查到的：「沒有人用這個位移寫它」

`tools/ida_disp_users.py` 掃全庫位移 `0x7000`：

```
==== +7000h：1 處 ====
  sub_1B1B1    0001B1DC 讀  mov dl, es:[di+7000h]
```

**只有一處，而且是讀。** 而建置常式 `sub_1BB3C` 的清空只到 0x6FFF：

```asm
0001BB4B  es = cs:word_1D2FA
0001BB52  cx = 3800h / xor ax,ax / rep stosw   ; ★ 0x3800 words ＝ 0x7000 bytes
0001BB59  di = 0 / cx = 1000h
0001BB5E  call sub_1BB6D ×4096                 ; 每格展開七層（只設 bit 7）
```

`0x7000` 正好是**七層** × `0x1000`——所以那一段清的是通行圖本身，
**沒有碰到 0x7000 以上**。

⚠ 但它不可能恆為 0：`and dl, dl / jz` 之後走的是 `sub_1C653` ＋ CF=1（失敗），
若恆為 0 就**沒有任何水平移動會成功**。所以一定有人寫，
只是**不透過 `+0x7000` 這個位移**——例如把 `di` 預設成 `0x7000` 之後直接
`stosb`／`mov es:[di], al`，那種寫法位移掃描抓不到。

**下一步**：在 `word_1D2FA` 段上找 `di ≥ 0x7000` 的寫入端
（`sub_1B240`／`sub_1B3B2`／`sub_1B824` 寫的是 `es:[bx−0x7000]` ＝ `+0x9000`，
是另一張圖，不是這一張）。

| 項目 | 現況 |
|---|---|
| ~~那兩張地面高度圖是誰填的~~ | **已解**：`sub_1BBA6` → `sub_1BC39`，在 `word_1D2FC` 段（[`../re/63`](../re/63-ground-plane-map.md)）|
| `Field.gateX` 與登城點 | gateX 在三張抽樣圖上**正好就是可破壞城壁那一格**。`doScaleWall` 已經把它當目標，但爬不上去 |
| 繞路點清單的演算法 | `0x1800 + 兵編號 × 128`，`loc_1BD46` 算（[`../re/11`](../re/11-tactical-battle.md) §5.15）。解出來之後 `FindPathForcing` 那條近似要換掉 |
| 攻城計時器與突破時間的關係 | 大將體力 100 起、每 10 幀掉 1、50 觸發退卻 ⇒ **攻方只有約 500 幀**。爬牆接上之後要重量一次，確認這個預算合理 |

## 6. 怎麼重跑

量測用的是一次性 probe（沒有留在 repo）。要重跑就照這個骨架：
用 `battle.Parse` 讀三個原版檔、`NewFieldFromTiles(lib.Tiles(n), lib.Heights(n), lib.GateX(n))`
建戰場、`LoadFormations` 讀陣形表，雙方 `Deploy` ＋ `Place` 之後
每幀累加各實體的 `Durability` 看有沒有變。
