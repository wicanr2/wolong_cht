## 3. ⭐ 為什麼改動一個像素都沒動到

`spec/128` 改的是「隊長倒下之後那一隊的待機兵」。這四個取樣點裡
**沒有一個走到那個狀態**——野戰第 52 拍還在開場對白，攻城前 300 拍
攻方在敲牆，隊長（每隊第 0 格）都還活著。

⚠ **所以這一輪的對拍證明的是「沒有回歸」，不是「改對了」。**
改動本身的驗收靠單元測試（`spec/128` §3），而其中一支是專門為了
**測接線**才加的——前兩支直接呼叫 `applySquadLeaderGone`，
把 `Step()` 裡那一行拔掉照樣綠（突變測試發現）。

## 4. ⭐ 與 `58` 的差異出自 `db7859f`，而且那一輪就量過了

**二分定位（2026-09-04）**：同一組指令、同一份存檔、同一個 seed，
沿 `60d24dd..HEAD` 逐個 checkout 重跑攻城第 160 拍：

| commit | `field` |
|---|---:|
| `60d24dd`（`58` 那一輪）| **0.85%** |
| `df05111` `\1` 與 `\4` 代入呼び名 | 0.85% |
| **`db7859f` 原版的尋路是反應式的** | **0.99%** ← 分界 |
| `6026c8c` 之後一路到 `HEAD` | 0.99% |

⚠ **這不是回歸，而且不是新發現。**
[`../spec/120`](../spec/120-pathfind-request-queue.md) §4 當天就寫了同一組數字
（0.85% → 0.99%、`sb-minimap` 1.64% → 1.72%、四個 PASS 區仍 0 px），
裁定是「尋路節流只改變兵走到同一格的**時刻**，單張截圖上分不出
『這一幀誰在重算』。**位置差，不是畫壞**」。
把尋路接成原版的反應式佇列是**更像原版**，而同一個人為取樣點
（第 160 拍）的差異因此變大——⭐ **對拍數字上升不自動等於退步。**

### 4.1 這一段是白走的，而且成因寫在專案規則裡

初版把它記成「`58` 的數字漂了、成因沒查」，然後花一整輪去二分。
**答案在同一天寫的另一份文件裡**，grep 那兩個數字（`0.99` 或 `1.72`）
一次就會中。`CLAUDE.md` §7 第 1 條與 §10 的五張表講的就是這件事，
而這一次沒有觸發——因為它不像「動手挖」，像「順手記一個觀察」。

⭐ **寫下「成因沒查」之前，要先 grep 那個數字本身。**
缺口欄位是有成本的：它會讓之後每一輪都繞著一個已經有答案的東西打轉。

### 4.2 引用對拍數字要連 commit 一起寫

`58` 與這一份都沒有錯——差的是**基準點**，而兩份都只標了日期。
同一天之內就可能跨過一個改變軌跡的 commit，所以

> 對拍數字 ＝ （原版影格, remake commit, 取樣點）三元組，缺一個就對不起來。
