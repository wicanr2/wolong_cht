# 05 — `MMAP.*` 大地圖

**狀態：`MMAP.MDL`、地圖尺寸、自動連接與 `MMAP.MCH` 物件圖形入口
confirmed；`MMAP.MAP` 的 RLE 見 [`docs/formats/06`](06-mmap-rle.md)，
也 READY。事件 12 object type 1／2 已接入呈現層，原版 timer 時序仍是
呈現層 substitute。**

- 日期：2026-08-07
- 出處：`workplace/ida/dosv/KI.EXE.i64`（`sub_1E48A`／`sub_1E4CE`／`sub_1E57F`）
  ＋ PC-98 實機畫面（`docs/playtest/02`）
- 工具：`tools/grf.py`

## 1. `MMAP.MDL`：256 塊 16×16 地形圖塊（confirmed）

32,768 ÷ 128 ＝ **256 塊**，餘 0。像素格式與 `*GRF.DAT` 相同
（4 bpp plane-major，見 `docs/formats/03` §1）。

兩條獨立證據：

1. **算術**：128 B／塊正是 16×16 4bpp，整除無餘數。
2. **視覺**：解出來是草地、河流與海岸、山地、道路、城牆、建築物，
   與 PC-98 實機大地圖畫面的地形完全吻合。

繪製常式對 16×16 圖塊用 `ax = 1001h`（`ah`＝16 列、`al`＝1 → 每列 2 byte
＝ 16 px），與 `docs/re/03` §3 的參數拆法一致。

## 2. 地圖尺寸：384 × 256 格（confirmed）

`sub_1E4CE` 的掃描迴圈：

```asm
loc_1E4E2:
        mov     al, es:[di]
        …
        inc     di
        inc     cx
        cmp     cx, 180h        ; ← 一列 384 格
        jnz     short loc_1E4E2
        add     bp, 18h         ; ← 下一列：段 +0x18 ＝ +384 byte
        add     dx, 18h
        inc     ah
```

- 一列 **384 格**，每格 **1 byte**。
- 列跨距 384 byte → 格與 byte 一對一，沒有 padding。
- 展開後的緩衝區是 **98,304 B**（`sub_119CA` 用 `rep stosw` 清 0x8000＋0x4000 words）。
  98,304 ÷ 384 ＝ **256 列**。

**所以世界地圖是 384 × 256 格 ＝ 6,144 × 4,096 pixel。**
與社群資料說的「大中小城池、戰場、關口近 300 處，道路交錯複雜」對得上。

> 這也解釋了為什麼 `MMAP.MAP` 只有 80,716 B 卻要展開成 98,304 B：
> **檔案是編碼過的，`sub_1E48A` 負責展開。** 編碼方式未解（§4）。

### 2.1 ⭐ 檔頭那 4 byte 是長度，不是圖塊

`MMAP.MAP` 的前四個 byte 是 `00 80 01 00` ＝ 小端 u32 **98,304**，
正好等於地圖本體的大小。原版的載入器在讀第一個 byte 之前先 `LSEEK`
過它（`sub_1F655`，[`06`](06-mmap-rle.md) §3、[`../spec/113`](../spec/113-rle-length-header.md)），
**地圖本體是解壓輸出的第一個 byte。**

⭐ 這個頭夠特別：`00 80 01 00` 沒有相鄰重複，RLE 原樣吐出而且相位不變，
所以「連頭一起解、再切掉解出來的前四個 byte」也會得到同一張地圖。
過場圖沒有這個運氣（[`09`](09-cutscene-images.md) §1.1）。

把那四個 byte 當成圖塊讀不會報錯，也不會畫壞——整張地圖只是**往左移四格**，
而那四格會以兩個看似無關的「原版怪癖」現身：

| 症狀 | 真相 |
|---|---|
| 「據點記錄座標不是圖案中心，中心在右邊四格」 | 記錄座標**就是**中心格。192 座零例外 |
| 「鏡頭變數比畫面上 x=0 那一欄小 4」 | `word_1988E` **就是**那一欄（`sub_11F7F`：`word_1988E = word_19882 >> 4`）|

判準：`Tiles[y*384 + x]` 對 192 座據點**全部**落在中心格的值
（205／208／211）上；把長度頭當圖塊讀是 0 座。
**一個偏移能同時解釋兩個怪癖，就該懷疑怪癖是自己造的。**

## 3. ⚠ 訂正：那段不是「換圖塊」，是在建**道路連接關係表**

> `0x80`–`0x83` 是**方向碼**，不是圖塊編號；那段程式碼寫的是記錄，
> 不是地圖格的圖塊值（`sub_1E68C`）。

### 實際在做什麼

`sub_1E4CE` 逐格掃描地圖，對每一個落在 `0xCB`–`0xD3` 的格子，
檢查**四個方向**的鄰格是否落在 `0xB8`–`0xDD`：

> ⭐ **`0xCB`–`0xD3` 這九個值是據點中心，不是「道路格」。**
> 它們只出現在**據點記錄座標那一格**上（§2.1），
> 一般路面圖塊不在這個範圍（[`../re/67`](../re/67-city-emblem-on-strategy-map.md)）。
> 據點本來就是道路圖的節點，所以「掃它們建圖」與「它們是據點」不衝突——
> 但下面那句「把道路格換成節點編號」講的是圖的節點，不是地圖被改寫。


| 鄰格 | 偏移 | 方向碼 |
|---|---|---|
| 左 | `[di-1]` | `0x80` |
| 右 | `[di+1]` | `0x81` |
| 上 | `[di-180h]`（−384 ＝ 一列） | `0x82` |
| 下 | `[di+180h]`（+384） | `0x83` |

**四個方向都看**（初版只讀到左右，把上下漏了）。

命中就呼叫 `sub_1E68C`／`sub_1E6FF`（兩支內容相同），寫一筆 8 byte 記錄：

```asm
mov     [si],   di          ; +0  地圖內的偏移（＝ y×384 + x）
mov     [si+2], bp          ; +2  段基底
mov     [si+4], cx          ; +4  欄
mov     [si+6], ah          ; +6  列
mov     [si+7], al          ; +7  **方向碼 0x80–0x83**
mov     es, dx
mov     al, cs:byte_1E47F   ;     流水號
mov     es:[di], al         ;     蓋回地圖格
```

`si` 每寫一筆 `+8`，`sub_1E4CE` 的 `bx = 1800h` ＝ **6,144 byte ＝ 768 筆**上限。
`sub_1E717` 之後就是掃這 768 筆（`cmp byte ptr es:[bx+7], 80h` ——
比對的正是方向碼那個欄位）。

### 推論：這是行軍用的道路網圖

**強證據，未定案。** 支持的理由：

- 記錄裡存的是「位置 ＋ 方向」，那是**邊**不是像素。
- 地圖格被蓋成流水號，等於把格子換成**節點編號**。
- `docs/re/05` 已確認軍團記錄的 `+0x1A` 就是地圖格偏移
  ——軍團在同一個座標系上移動。
- 社群資料說本作「道路交錯複雜，可以選擇多種不同的進攻路線」，
  那需要一張路網。

**還沒驗的**：`sub_1E717` 建出來的東西實際被誰用。
在那之前不要把「行軍尋路」寫成定論。

### 這對 remake 的意義變了

初版的結論是「照抄查表會讓接邊斷掉」——**那個結論不成立**，
因為根本沒有換圖塊這回事。真正的意義是：

**地圖載入不是純解碼，還有一個前處理階段**會從據點中心那九個值
建出道路圖。remake 若只做解碼、跳過這一步，就沒有那張連接關係表。

⚠ **前處理不改寫地圖本身**：`sub_1E4CE` 與 `sub_1E57F` 只讀 `es:[di]`，
寫的是另外一張 8 byte 一筆的記錄表。畫面上那一格畫出來的仍然是圖塊
`205`／`211` 本身——原版另外在上面疊了一個**勢力色的徽記**
（[`../re/67`](../re/67-city-emblem-on-strategy-map.md) §3）。
