## 1. 外層：4 byte 長度頭 ＋ 與 `MMAP.MAP` 同一種 RLE

`D7END.EXE` 的 `sub_114E9` 與 `KI.EXE` 的 `sub_1F5E7` 是**同一個演算法**
（[`06`](06-mmap-rle.md)）：沒有逃脫字元，連續兩個相同的 byte 之後那一個
是「再重複幾次」，次數 0 表示那兩個就只是字面值。

⭐ **這一條是整個格式的鑰匙。** 先前 `END_S*` 被當成未解，是因為
播放器裡三個 consumer 的來源位移（`0`／`0xBB8`／`0xE74` 段）換成 byte 之後
**比檔案本身還大**——那些位移指的是**解壓後**的緩衝區。

### 1.1 ⭐ `[HARD]` 前 4 byte 是解壓長度，載入器 `LSEEK` 跳過它

開檔的子程序（`D7OPEN.EXE` 的 `sub_10E04`、`KI.EXE` 的 `sub_1F655`、
`D7END.EXE` 同一段）在讀第一個 byte 之前先 `int 21h ax=4200h, cx=0, dx=4`。
跳過的 4 byte 是**小端 u32 ＝ 解壓後的長度**，
兩版各 20 個檔宣告值與跳頭解出來的長度**逐檔相等**：

| 檔 | 壓縮（DOS/V）| 宣告 ＝ 解壓 |
|---|---:|---:|
| `END_S1` | 40,999 | **91,200** |
| `END_S2`–`S12` | 10,637–81,596 | **128,000** |
| `GAMEOVER` | 16,963 | **128,000** |
| `OPEN_S1` | 51,403 | **78,016** |
| `OPEN_S2`／`S3`／`S4` | 212,513–319,264 | **384,000** |
| `OPEN_S5` | 55,506 | **288,000** |
| `OPEN_S6` | 71,150 | **128,000** |

**沒有「尾巴沒編進去」這回事**——跳頭之後每一個檔都解到剛好。
從 0 開始解會在某一處掉相位，長度差幾十個 byte、內容整體位移；
一張 320 px 寬的圖會在 x ＝ 160 冒出一條垂直接縫，左右兩半互換。
**判準是長度：差一個 byte 就是錯的。**

⚠ `END_S13`／`S14`／`S15` 不走這條路——那三個是中文字型與人名字
（[`../re/29`](../re/29-font-service-int15.md)、[`10`](10-end-s15-namechars.md)），
前 4 byte 不是長度。

⚠ **`GAMEOVER.DAT` 也是這一族**：128,000 B，版面與 `END_S*` 同（§2），
畫面是燭光下兩人對談的加框場景。它不由 `D7END.EXE` 播——那一支只放
`END_S1`–`S12`（[`../re/70`](../re/70-d7end-ending-player.md) §1）。

## 2. 內層：640 × 400、16 色、EGA 四平面

一張畫面 128,000 B ＝ 640 × 400 ÷ 8 × 4。版面來自 `sub_10293` 的兩次貼圖：

```asm
ds = 影像段        / si = 0     / bx = 0      / ax = 0C828h / sub_1178A
ds = 影像段+0FA0h  / si = 0     / bx = 3E80h  / ax = 0C828h / sub_1178A
```

- `0xFA0` 段 ＝ **64,000 B**；`0x3E80` ＝ 16,000 ＝ 200 列 × 80 B
- 所以是**上下兩半各 200 列**，各 64,000 B

一半之內是**平面優先**：四個平面各 16,000 B（200 列 × 80 B）依序排。
`sub_1178A` 對「enable set/reset」依序寫 `0x0E`／`0x0D`／`0x0B`／`0x07`
（＝ `~1`／`~2`／`~4`／`~8`），所以**來源的第 n 塊就是平面 n**，
色號 ＝ 四個平面同一位元湊出來的 0–15。

```
色號(x, y) = Σ  bit(  buf[ half(y) + p×16000 + (y mod 200)×80 + x÷8 ],  7 − x mod 8 ) << p
             p=0..3
half(y) = 0（y < 200）或 64,000
```

### 2.1 ⭐ 第一幕是 **320 px 寬**，不是 640

`END_S1` 宣告 91,200 B，用 §2 的 640 版面去畫會看到亭子**左右各一份**
——那就是寬度猜錯的樣子。實際是 320 px 寬，貼在 x ＝ 160
（`sub_1016D` 的 `di = 0x14`，粗格單位）。三塊在緩衝區裡首尾相接：

| 塊 | 起點 | 長度 |
|---|---:|---:|
| 平面 0／1（交錯，400 列 × 80 B）| 16,000 | 32,000 |
| 平面 2（280 列 × 40 B）| 48,000（`0BB8h` 段）| 11,200 |
| 平面 3（整張 640 × 400）| 59,200（`0E74h` 段）| 32,000 |

⭐ **加起來剛好 91,200 ＝ 檔頭宣告的長度。** 這是版面對不對最硬的一道檢查：
三塊的位移全部出自機器碼，而總和落在宣告值上是獨立的第二份證據。

### 2.2 ⭐ 開場的 `OPEN_S2`–`S4` 是 12 幀動畫

384,000 ＝ **12 × 32,000**，一幀 320 × 200 × 四平面，
平面 p 的第 y 列在幀內 `p × 8000 + y × 40`
（`sub_10586`，[`../re/76`](../re/76-d7open-opening-player.md) §7）。
`sub_10538` 先把第 0–3 幀循環六遍再走一次 0–11，每幀之間停 4 個計時單位。

量幀間差異看得到同一個結構：`f0` 與 `f4` 只差 3 個 byte，
`f0` 與 `f1` 差 6.0k——**四個相位 × 三個階段**，
前八幀幾乎只有旗幟在動。`OPEN_S5`（288,000）走 CRTC 硬體捲動，
`OPEN_S1`（78,016）與 `OPEN_S6`（128,000）各有自己的版面（同 §7、§9）。

## 3. 色盤：一幕一組

`ENDPAL.BRG` 是 192 色 ＝ **12 組 × 16**，而結局正好 12 幕。
`sub_1035F(al = 幕號, ah = 淡入階)` 的 `al` 就是幕號——
**第 n 幕用第 n 組**。實測：`END_S2`（第 1 幕，從 0 起算）配第 1 組
才是暖色的山景，配第 0 組會變成藍白色。

開場同一套：`OPENPAL.BRG` 288 B ＝ **6 組 × 16**，
`sub_10615(al = 組, ah = 淡入階)` 的 `si = al × 48`，
**第 n 組配第 n＋1 幕**（[`../re/76`](../re/76-d7open-opening-player.md) §3）。

淡入淡出的色階算式與 `GAMEPAL.BRG` 共用：
`out = ((v << 4) × 亮度 + 0x80) >> 8`，亮度 0–16
（[`../re/02`](../re/02-palette-routine.md) §4，`sub_10AE0`／`sub_103DC` 同一條）。

格式與 `GAMEPAL.BRG` 相同（[`02`](02-brg-palette.md)）。
