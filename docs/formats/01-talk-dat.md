# 01 — `TALK.DAT` 訊息表格式

**狀態：READY**（可以照這份實作）

- 日期：2026-08-07
- 輸入：
  - `workplace/orig/dosv/TALK.DAT` 34,182 B（松崗繁中版）
  - `workplace/orig/pc98/TALK.DAT` 45,718 B（PC-98 日文版）
- 工具：`tools/talkdat.py`
- 驗收：**兩版都 byte-for-byte round-trip 通過**
  （`talkdat.py verify … cp950` ／ `… cp932`，各 1,022 則、零逃脫位元組）

## 1. 檔案結構

```
0x0000 ┌────────────────────────────────┐
       │ 偏移表：1024 筆 uint16 LE       │  2,048 B
       │   [0..1021] 每則訊息的起點      │
       │   [1022]    結束哨兵            │
       │   [1023]    0（未使用）         │
0x0800 ├────────────────────────────────┤
       │ 訊息本體：1,022 則              │  檔案剩餘全部
       └────────────────────────────────┘
```

兩版的偏移表**都是 1024 筆、訊息都是 1,022 則**——同一份程式的兩個語言版。

### ⚠ `[1022]` 是「最後一個 byte 的位移」，不是 one-past-end

`dosv` 的 `[1022] = 34181`，而檔案長 34,182 B。
**照 `[1022]` 切最後一則會少一個 byte**，寫回去就對不上。
最後一則要讀到 EOF。

（`pc98` 同理：`[1022] = 45717`，檔長 45,718。）

## 2. 訊息結構

一則訊息就是**若干個 NUL 結尾的行**：

```
行1 00 行2 00 行3 00 …
```

`dosv` #0：

```
b'\xb6i\xa6\xe6\xb35\xb6\xa4\xbds\xb2\xd5\xa1C\x00\xbd\xd0\xbf\xef\xbe\xdc\xaaZ\xb1N\xa1C\x00\x00'
    進行軍隊編組。       NUL   請選擇武將。           NUL  （空行）NUL
```

### ⚠ 結尾的空行是資料，不是格式規定

不是每則都以 `00 00` 收尾：

| 收尾 | 則數（dosv） |
|---|---|
| 一個 NUL（沒有空行） | 78 |
| 兩個 NUL（一個空行） | 944 中的大多數 |
| 三個 NUL（兩個空行） | #1021 等少數 |

空行是對話框裡的留白。**解析時把結尾空行「正規化」掉，就寫不回去了**——
這是本格式最容易踩的一個坑（實際踩過，見 §6）。

行數分佈：

| 行數 | dosv | pc98 |
|---|---|---|
| 1（空訊息） | 78 | 78 |
| 2 | 124 | 46 |
| 3 | 672 | 283 |
| 4 | 142 | 610 |
| 5 | 2 | 5 |
| 6 | 4 | 0 |

**78 則空訊息兩版數量相同**——保留槽位，不是資料損壞。

### 2.1 那 78 則全部落在八格變體區，而且只有三種樣式

空訊息**沒有一則在 `0x196` 以下**：全部在 ×8 變體區（§3、[`../re/25`](../re/25-message-variants-and-personnel.md) §1），
而且只出現在 18 個組裡，樣式只有三種（`tools/talk_variants.py --empty`，兩版逐格相同）：

| 空的是哪幾格 | 有字的是 | 組數 | 例 |
|---|---|---:|---|
| 0、1、2 | 3–7（臣下型）| 9 | `0x199` 格 3「若能給我洗刷污名的機會，就萬幸之至。」|
| 3–7 | 0–2（主公型）| 6 | `0x196` 格 0「軍師！怎麼把國家的財政搞成了赤字，快設法解決！！」|
| 1–7 | 只有格 0 | 3 | `0x1A1` 格 0「解散軍團。」|

⭐ **前兩種就是說話型的補集。** 八格由武將記錄 `+0x1E` 選一格
（0–2 主公型／3–7 臣下型，[`../mechanics/60`](../mechanics/60-personnel.md) §3），
所以**只有臣下會說的情境**（打了敗仗回來道歉）把 0–2 留白，
**只有君主會說的**（罵軍師財政赤字）把 3–7 留白。
9 × 3 ＋ 6 × 5 ＋ 3 × 7 ＝ **78**，一則不多一則不少。

⚠ **兩版一起看才分得出「這一格本來就沒有」與「松崗版漏譯」**——
松崗版是譯本，漏譯的症狀同樣是空字串。兩版的空格位置**逐格相同**，
所以這 78 則是原始設計，不是中文版的缺漏。

第三種樣式（只有格 0）的三組是 `0x1A1`「解散軍團。」、
`0x1AD`「哼！看來是我軍的勝利了。」、`0x1AE`「你哪裡是我的對手，下次再來吧！！」——
**它們的呼叫端有沒有傳 `ah`、為什麼不需要變體，還沒讀**（見 §7）。

## 3. 變數插入：ASCII `\` ＋ 一位數字

```
\2受到\1兵馬   ／   的攻擊，被攻陷了！！
\2が\1の軍勢   ／   の攻撃を受け陥落しま   ／   した！！
```

用到的標記共 **六種**，`\5` 不存在：

| 標記 | dosv 出現 | pc98 出現 |
|---|---|---|
| `\1` | 102 | 108 |
| `\2` | 37 | 38 |
| `\3` | 85 | 84 |
| `\4` | 34 | 35 |
| `\6` | 72 | 74 |
| `\7` | 18 | 18 |

`KI.EXE` 的訊息格式化器（formatter）已把其中一段定案。`sub_1075B`（線性位址
`0001075B`）依訊息索引取偏移，`sub_1084A`（`0001084A`）逐字讀取訊息；遇到
`\N` 就以 `CS:[SI+08A4h]` 的七項跳躍表分派。這裡的 `SI` 是訊息游標，`DI`
是呼叫端建立的 `SS` 參數堆疊游標。

- `\6` 的處理器（handler）是 `0001097E`：讀取並消耗 `SS:[DI]` 的一個 16 位元參數，
  `DI += 2`，再把文字繪製座標 `DX` 左移 `0x30`；它不繪出該參數。因此
  `\6` 是**會消耗參數的排版控制標記**，不是已證實的說話者名稱。
- `\7` 的處理器（handler）是 `00010984`：同樣消耗一個 16 位元參數，接著進入
  `sub_1062F` 的圖形／數值繪製路徑；它與金額欄位同時出現的文意相符，但數值
  格式仍以該 handler 的後續常式為準。
- `\1`／`\2`／`\3`／`\4` 的資料來源已可由 handler 看到部分記錄偏移，完整的
  文字語意仍保留為未定案，不能只靠翻譯上下文升格。

### ⚠ 索引 ≥ `0x196` 不是一則訊息，是一組八個變體

`sub_1075B` 在取偏移**之前**先換算索引（`00010763`–`0001077C`）：

```
索引 < 0x196 → 直接用
索引 ≥ 0x196 → 0x196 + (索引 − 0x196) × 8 + ah
```

所以 `0x196`（406）之後是**八格一組**，呼叫端的 `ah` 選組內第幾個。
直接查第 `0x19C` 格會看到空的——那一格不是訊息，是組編號。

**對校訂是硬約束**：`#406` 之後的每一則都是某組的第 N 個變體，
語氣要跟同組另外七則一起看；只改其中一格等於只改了八分之一的說法。
完整的 13 個組與對照見 [`../re/25-message-variants-and-personnel.md`](../re/25-message-variants-and-personnel.md) §1。

上述位址是 `KI.EXE` 的 IDA 線性位址，不是檔案偏移；證據為
`workplace/ida/dosv/func-sub_1075B-current.txt`、
`func-sub_1084A-current.txt`，輸入 `KI.EXE` SHA-256
`FFFEBA985231CDA4D636E93D10F598470B1F691D00275E4AA38E285893D43868`，工具為
IDA Pro 9.4。

### ⚠⚠ 不能用 regex 找 `\N`

**Big5 與 Shift-JIS 的第二個 byte 都可能是 `0x5C`（`\`）。**
拿 `re.findall(rb'\\(.)')` 掃會把中文字切一半，掃出一堆假標記
——實際踩過，第一版就是這樣炸的。

**必須逐字掃描**：先判斷目前這個 byte 是不是雙位元組字的第一個 byte
（Big5 `0x81`–`0xFE`；Shift-JIS `0x81`–`0x9F` 與 `0xE0`–`0xFC`），
是就整組吃掉，`0x5C` 只有落在非雙位元組字的位置才是標記。

## 4. 編碼：要用 `cp950` 與 `cp932`，不是 `big5` 與 `shift_jis`

| 版本 | 正確編碼 | 用 `big5`／`shift_jis` 的後果 |
|---|---|---|
| dosv | **`cp950`** | `F9D8`（「裏」，Big5 罕用字區）解不開 |
| pc98 | **`cp932`** | 部分字編回去的 byte 與原檔不同 |

改用 `cp950`／`cp932` 之後，**兩版的無法還原位元組都是 0**。

> **這個坑差點變成一條錯誤結論。** 第一版用 `big5` 解，`dosv` #225 出現
> `這哪<f9>堿O什麼好策略？`，看起來就像松崗版打錯字。
> 實際上那是合法的「裏」，**錯的是我的解碼器不是原版**。
> 訂正比新結論需要更硬的證據（`CLAUDE.md` §8 第 7 條）——
> 宣告原版有錯之前，先確認自己的工具是對的。

### `[HARD]` 只信「解得開**而且**編回去一模一樣」的字

Python 的轉換表與 1994 年的原版不完全一致。光靠 decode 成功不足以保證寫得回去，
而寫不回去的中文化工具是不能用的。`talkdat.py` 的 `_safe_pair()` 對每個字
做一次 decode → encode → 比對，不通過的一律退回 `<xx>` 逐位元組逃脫。

## 5. 排版：行寬

| | 最寬行 | 剛好滿寬的行數 |
|---|---|---|
| dosv | **10 全形字** | 796 |
| pc98 | 20 全形字 | — |

`dosv` **沒有任何一行超過 10 字**，而且有 796 行剛好 10 字
→ **中文版是硬斷行，斷在 10 字**。日文版最寬到 20 字。

這代表：`TALK.DAT` 存的是**已經排好版的行**，不是連續文字。
**remake 不要沿用這個機制**——重寫版存整段文字，排版交給排版層
（`CLAUDE.md` §7）。原版的斷行位置仍要記錄，那是保存的一部分。

## 6. 工具

```sh
tools/py.sh tools/talkdat.py verify workplace/orig/dosv/TALK.DAT cp950
tools/py.sh tools/talkdat.py export workplace/orig/dosv/TALK.DAT cp950 out.json
tools/py.sh tools/talkdat.py build  out.json cp950 new.DAT
tools/py.sh tools/talkdat.py diff   workplace/orig/dosv/TALK.DAT cp950 \
                                workplace/orig/pc98/TALK.DAT cp932
```

抽出的 JSON 在 `translations/extract/talk-{dosv,pc98}.json`。

## 7. 還沒解的

| 缺口 | 現況 |
|---|---|
| `\1`／`\2`／`\3`／`\4` 的**文字語意** | 機制已解（§3：`sub_1075B` 換算索引、`sub_1084A` 逐字讀、`CS:[SI+08A4h]` 七項跳躍表分派），`\6`（排版控制，消耗一個 16 位元參數後 `DX` 左移 `0x30`）與 `\7`（走 `sub_1062F` 的數值繪製）兩支 handler 也定案了。**這四支的 handler 讀哪個記錄欄位沒逐一追完**——remake 目前用的是實務推定（`\1` 武將名、`\2` 據點名、`\4` 軍師名），不是機器碼定案 |
| ~~偏移表 `[1023] = 0`~~ | **對齊用的填充（強證據，2026-09-02）**：1,022 則訊息只需要 1,023 筆（1,022 個起點 ＋ 1 個哨兵），而表做成 1,024 筆 ＝ 2,048 B ＝ `0x800`，本體正好從 `0x800` 開始。讀取端 `sub_1075B` 是 `shl cx,1 / mov si,cx / mov si,[si]`，**沒有任何邊界檢查**，所以它也不是終止哨兵；要碰到 `[1023]` 得先有訊息索引 1022，而那要求組 `0x1E3`——第 78 組，資料裡只有 77 組。兩版皆為 0 |
| ~~78 則空訊息的索引位置有沒有規律~~ | **有，而且完全規律**（confirmed，2026-09-02）：全部在變體區，18 組、三種樣式，就是說話型的補集。見 §2.1 |
| 只有格 0 有字的三組（`0x1A1`／`0x1AD`／`0x1AE`）| 呼叫端傳不傳 `ah`、為什麼不需要八格變體，未讀。`0x1AD`／`0x1AE` 像單挑台詞，但不在 [`../re/75`](../re/75-duel-talk-audit.md) 盤過的 `0x1B6`–`0x1CD` 範圍內 |
| 訊息索引與遊戲事件的對應 | 逐則的顯示時機沒有全表。**已對出來的散在各規格**（進言 [`../spec/44`](../spec/44-advise-original-text.md)、遷都 [`../spec/64`](../spec/64-capital-relocation-report.md)、結局 [`../spec/30`](../spec/30-victory.md)），未讀的部分見 [`../re/24`](../re/24-unread-function-catalogue.md) |

⚠ **不要把「remake 填得進去」當成「語意已定案」。** `cmd/wlgame` 有一份
帶通用字樣的 fallback（`'1': "武將"`、`'2': "據點"`…），畫面上看起來合理，
但那是推定值——**畫得出來不是證據**。
